    7. Funktionale Schnittstellen, Lambdas und Ereignisse

    In vielen Programmen müssen wir einer Methode nicht Daten, sondern Verhalten übergeben: das Sortierkriterium, die Filterbedingung oder die Verarbeitung, die ausgeführt werden soll, wenn etwas geschieht. Java begegnet diesem Bedarf mit einem einfachen Konzept, auf dem dieses ganze Kapitel beruht: die funktionale Schnittstelle, also eine Schnittstelle, die nur eine einzige abstrakte Methode deklariert. Ein Objekt, das eine solche Schnittstelle implementiert, „trägt“ eine Funktion, die in einer Variablen gespeichert, als Parameter übergeben, als Ergebnis einer Methode zurückgegeben und nach Belieben ausgeführt werden kann.

    Vor Java 8 (2014) musste man für jedes auszudrückende Verhalten eine Klasse schreiben – oft eine anonyme Klasse –, was umständlich war. Java 8 führte Lambda-Ausdrücke und Methodenreferenzen ein, mit denen sich dieses Verhalten in einer einzigen Zeile schreiben lässt. Wir haben sie bereits ohne nähere Erläuterung mit der Stream-API in Kapitel 5 verwendet: In [persons.stream().filter(p -> p.age() >= 18)] übergeben wir der Methode [filter] ein Lambda, also eine Instanz einer funktionalen Schnittstelle. Dieses Kapitel erklärt, was hinter dieser Syntax steckt. Es endet mit Ereignissen, die Java mithilfe von „Listenern“ behandelt: Objekte – oft Lambdas –, die sich bei einem Sender registrieren, um über das informiert zu werden, was dort geschieht. Grafische Benutzeroberflächen in Java (Swing, JavaFX) und Web-Frameworks beruhen gleichermaßen auf diesem Mechanismus: Ein Klick auf eine Schaltfläche oder das Eintreffen einer (HTTP-)Anfrage wird den registrierten Listenern signalisiert. Dieser Kurs behandelt keine grafischen Benutzeroberflächen; alle Beispiele sind Konsolenprogramme.

    Die Programme dieses Kapitels sind kompakte Quelldateien im Ordner [07-lambdas]. Sie werden mit [java LambdasNN.java] ausgeführt. Beachten Sie, dass eine kompakte Quelldatei automatisch das gesamte Modul [java.base] importiert: Die Schnittstellen der Pakete [java.util.function], [java.util], oder [java.util.concurrent] können dort ohne [import]-Anweisungen verwendet werden.

    7.1. Vordefinierte funktionale Schnittstellen

    7.1.1. Das Konzept der funktionalen Schnittstelle

    Eine funktionale Schnittstelle ist eine Schnittstelle mit genau einer abstrakten Methode. Sie darf zusätzlich beliebig viele [default]- und [static]-Methoden haben (siehe Kapitel 4): Diese zählen nicht mit. Diese eine abstrakte Methode beschreibt ein Muster (auch Signatur oder Form genannt) einer Funktion: die Typen ihrer Parameter und den Typ ihres Rückgabewerts. Eine Variable vom Typ der Schnittstelle kann dann auf jedes Objekt verweisen, das eine Funktion dieser Form bereitstellt, und sie durch Aufruf der Methode ausführen.

    Das älteste Beispiel ist die Schnittstelle [java.lang.Runnable], die seit Java 1.0 existiert und eine auszuführende Aufgabe darstellt (wir kommen in Kapitel 8 im Zusammenhang mit Threads darauf zurück). Sie besteht aus einer einzigen Methode: [void run();]. Sie beschreibt eine Funktion,

    • die keine Parameter hat;
    • die kein Ergebnis zurückgibt ([void]).

    Es gibt drei Möglichkeiten, ein Objekt vom Typ [Runnable] zu erzeugen:

    • eine Klasse schreiben, die die Schnittstelle implementiert, entweder benannt oder anonym. Das war vor Java 8 die einzige Möglichkeit;
    • einen Lambda-Ausdruck schreiben: [Runnable task = () -> IO.println("task");];
    • eine Methodenreferenz auf eine vorhandene Methode mit der passenden Form schreiben: [Runnable task = Functions::display;].

    In den beiden letzten Fällen erzeugt der Compiler das Objekt, das die Schnittstelle implementiert, selbst: Das Lambda oder die referenzierte Methode wird zum Rumpf der Methode [run]. Die Funktion wird dann durch Aufruf der Schnittstellenmethode ausgeführt: [task.run()]. Anders als andere Sprachen hat Java keine eigene Aufrufsyntax: Die Schnittstellenmethode wird immer über ihren Namen aufgerufen ([run], [apply], [test] …).

    7.1.2. Schnittstellen im Paket java.util.function

    // die vordefinierten funktionalen Schnittstellen von Java

void main() {
    // 1 - Runnable: kein Parameter, kein Ergebnis: void run()
    Runnable task = new Runnable() {
        @Override
        public void run() {
            Functions.display();
        }
    };
    // Kurzform: eine Methodenreferenz
    task = Functions::display;
    // Ausführung: Wir rufen die einzige abstrakte Methode der Schnittstelle auf
    task.run();

    // 2 - BiFunction<T, U, R>: zwei Parameter, ein Ergebnis
    BiFunction<Integer, Integer, Integer> operation = Functions::add;
    IO.println("operation.apply(2, 3)=" + operation.apply(2, 3));
    // Supplier<T>: kein Parameter, ein Ergebnis
    Supplier<String> greet = Functions::greet;
    IO.println("greet.get()=" + greet.get());
    // primitive Version: IntBinaryOperator, int applyAsInt(int, int), ohne Boxing
    IntBinaryOperator multiply = Functions::multiply;
    IO.println("multiply.applyAsInt(2, 3)=" + multiply.applyAsInt(2, 3));

    // 3 - Consumer<T>: ein Parameter, kein Ergebnis
    Consumer<String> write = IO::println;
    write.accept("Consumer<String> executed IO.println");

    // 4 - Predicate<T>: ein Parameter, ein boolesches Ergebnis
    Predicate<Integer> isEven = Functions::isEven;
    IO.println("isEven.test(8)=" + isEven.test(8));
    List<Integer> numbers = new ArrayList<>(List.of(3, 8, 1, 6, 5, 4));
    // removeIf von Collection erwartet ein Predicate
    boolean modified = numbers.removeIf(isEven);
    IO.println("even numbers removed: " + modified + ", remaining: " + numbers);

    // 5 - Comparator<T>: zwei Parameter vom Typ T, ein int-Ergebnis
    List<String> names = new ArrayList<>(List.of("Paul", "Mélanie", "Jo", "Sébastien"));
    names.sort(Functions::compareLengths);
    IO.println("sorted by length: " + names);

    // 6 - ein Lambda ist ein Objekt: die Instanz einer generierten Klasse, die die Schnittstelle implementiert
    IO.println("class: " + operation.getClass().getName());
    IO.println("interfaces: " + Arrays.toString(operation.getClass().getInterfaces()));
}

// die referenzierten Methoden, in einer Klasse zusammengefasst
// (die implizite Klasse einer kompakten Quelldatei kann nicht benannt werden)
class Functions {

    static void display() {
        IO.println("display() executed by Runnable.run()");
    }

    static int add(int n1, int n2) {
        return n1 + n2;
    }

    static int multiply(int n1, int n2) {
        return n1 * n2;
    }

    static String greet() {
        return "Hello";
    }

    static boolean isEven(int n) {
        return n % 2 == 0;
    }

    static int compareLengths(String s1, String s2) {
        return Integer.compare(s1.length(), s2.length());
    }
}

    7.2. Eigene funktionale Schnittstellen definieren

    Die vordefinierten Schnittstellen reichen oft aus, Sie können aber auch eigene definieren. Schreiben Sie dazu einfach eine Schnittstelle mit einer einzigen abstrakten Methode, zum Beispiel:

    • [interface Operation { int calculate(int n1, int n2); }]

    Diese Schnittstelle stellt eine Funktion dar, die zwei ganze Zahlen entgegennimmt und eine ganze Zahl zurückgibt. Im Vergleich zu [IntBinaryOperator]* hat der Typ *[Operation] einen Namen, der seinen Zweck beschreibt, seine Methode hat einen sprechenden Namen ([calculate] statt [applyAsInt]*), und seine Parameter haben Namen ([n1], [n2]), die Entwicklungswerkzeuge anzeigen. Ihr ist die Annotation [@FunctionalInterface]* vorangestellt: Sie ist nicht erforderlich, weist aber den Compiler an zu prüfen, dass die Schnittstelle funktional ist, und dokumentiert die Absicht des Entwicklers.

    Eine Variable [op] vom Typ [Operation] verweist immer nur auf eine Funktion zur Zeit. Anders als andere Sprachen, die „Multicast-Delegates“ anbieten, bietet Java keine Möglichkeit, mehrere Funktionen in einer einzigen Variablen zu speichern und alle mit einem einzigen Aufruf auszuführen: Bei Bedarf legt man die Funktionen in einer Liste ab und führt sie nacheinander aus. Genau das werden wir bei Ereignis-Listenern tun.

    // eigene funktionale Schnittstellen definieren

void main() {
    // eine Variable vom Typ Operation erhält die statische Methode increase
    Operation op = Calculations::increase;
    // wir führen die Operation aus
    int n = op.calculate(4, 7);
    IO.println("n=" + n);

    // Erzeugung eines Objekts c1 vom Typ Calculations
    var c1 = new Calculations();
    // wir speichern in op die Methode add des Objekts c1
    op = c1::add;
    n = op.calculate(2, 3);
    IO.println("n=" + n);
    // dann die Methode subtract von c1
    op = c1::subtract;
    n = op.calculate(2, 3);
    IO.println("n=" + n);

    // eine Variable referenziert nur eine Funktion: Um mehrere auszuführen, verwenden wir eine Liste
    List<Operation> operations = new ArrayList<>();
    operations.add(c1::add);
    operations.add(c1::subtract);
    operations.add((n1, n2) -> n1 * n2);
    for (Operation operation : operations) {
        IO.println("-> " + operation.calculate(10, 4));
    }

    // eine default-Methode der Schnittstelle erstellt eine neue Operation
    Operation squaredSum = ((Operation) c1::add).then(x -> x * x);
    IO.println("squaredSum.calculate(1, 2)=" + squaredSum.calculate(1, 2));

    // Operation und IntBinaryOperator haben dieselbe Form, sind aber zwei verschiedene Typen
    IntBinaryOperator other = op::calculate;
    IO.println("other.applyAsInt(5, 1)=" + other.applyAsInt(5, 1));

    // eine generische funktionale Schnittstelle
    Transformation<String, Integer> length = String::length;
    Transformation<Integer, String> stars = "*"::repeat;
    IO.println("length(\"Hello\")=" + length.transform("Hello"));
    IO.println("stars(5)=" + stars.transform(5));
}

// Definition einer funktionalen Schnittstelle: eine einzige abstrakte Methode
// die zwei ganze Zahlen als Parameter akzeptiert und eine ganze Zahl zurückgibt
@FunctionalInterface
interface Operation {
    int calculate(int n1, int n2);

    // eine default-Methode zählt nicht: Die Schnittstelle bleibt funktional
    default Operation then(IntUnaryOperator next) {
        return (n1, n2) -> next.applyAsInt(calculate(n1, n2));
    }
}

// eine generische funktionale Schnittstelle: T -> R
@FunctionalInterface
interface Transformation<T, R> {
    R transform(T value);
}

// eine Klasse, deren Methoden die Form der Schnittstelle Operation haben
class Calculations {
    // zwei Instanzmethoden
    int add(int n1, int n2) {
        IO.println("add(" + n1 + "," + n2 + ")");
        return n1 + n2;
    }

    int subtract(int n1, int n2) {
        IO.println("subtract(" + n1 + "," + n2 + ")");
        return n1 - n2;
    }

    // eine statische Methode
    static int increase(int n1, int n2) {
        IO.println("increase(" + n1 + "," + n2 + ")");
        return n1 + 2 * n2;
    }
}

void main() {
    // 1 - eine anonyme Klasse: Die die Schnittstelle implementierende Klasse wird an Ort und Stelle geschrieben
    IntBinaryOperator add = new IntBinaryOperator() {
        @Override
        public int applyAsInt(int n1, int n2) {
            return n1 + n2;
        }
    };
    IO.println("anonymous class: add(2, 3)=" + add.applyAsInt(2, 3));

    // 2 - dasselbe mit einem Lambda-Ausdruck (Java 8): Parameter -> Rumpf
    IntBinaryOperator subtract = (int n1, int n2) -> {
        return n1 - n2;
    };
    IO.println("block-body lambda: subtract(2, 3)=" + subtract.applyAsInt(2, 3));

    // 3 - die Parametertypen werden aus der Zielschnittstelle abgeleitet
    IntBinaryOperator multiply = (n1, n2) -> n1 * n2;
    IO.println("expression-body lambda: multiply(2, 3)=" + multiply.applyAsInt(2, 3));

    // 4 - ein einziger Parameter: Die Klammern sind optional
    IntUnaryOperator square = x -> x * x;
    Predicate<String> isEmpty = s -> s.isEmpty();
    IO.println("square(7)=" + square.applyAsInt(7) + ", isEmpty(\"\")=" + isEmpty.test(""));

    BiConsumer<String, Integer> repeat = (text, times) -> {
        for (int i = 0; i < times; i++) {

        }
        IO.println();

    BiConsumer<Object, String> listener = (_, _) -> IO.println("event received");

    Form
    Beispiel
    typisierte Parameter, Blockrumpf
    [(int a, int b) -> { return a + b; }]
    nicht typisierte Parameter, Ausdrucksrumpf
    [(a, b) -> a + b]
    ein einzelner nicht typisierter Parameter
    [x -> x * x]

    Die Parameter sind entweder alle typisiert oder alle nicht typisiert: Beides zu mischen ist nicht möglich. Bei einem Blockrumpf muss ein Lambda, das ein Ergebnis zurückgibt, wie eine Methode auf jedem Ausführungspfad eine [return]-Anweisung enthalten.

    Ein Lambda ist nicht ganz dasselbe wie eine verkürzt geschriebene anonyme Klasse. In einer anonymen Klasse verweist [this] auf die Instanz der anonymen Klasse; in einem Lambda verweist [this] auf das Objekt der Methode, die das Lambda umschließt. Außerdem erzeugt eine anonyme Klasse einen neuen Gültigkeitsbereich: Sie kann eine Variable mit demselben Namen wie eine Variable der Methode deklarieren, was ein Lambda nicht kann. Schließlich kann eine anonyme Klasse eine Schnittstelle mit mehreren Methoden implementieren oder von einer abstrakten Klasse erben, was mit einem Lambda unmöglich ist. In diesem Kurs verwenden wir Lambdas, wo immer es möglich ist.

void main() {
    // 1 - Function: andThen (erst this, dann die andere) und compose (erst die andere)
    Function<Integer, Integer> plusOne = x -> x + 1;
    Function<Integer, Integer> timesTwo = x -> x * 2;
    IO.println("plusOne.andThen(timesTwo).apply(5)=" + plusOne.andThen(timesTwo).apply(5));
    IO.println("plusOne.compose(timesTwo).apply(5)=" + plusOne.compose(timesTwo).apply(5));
    // eine aus einer Liste von Funktionen aufgebaute Verarbeitungskette
    List<UnaryOperator<String>> steps =
            List.of(String::strip, String::toLowerCase, s -> s.replace(' ', '-'));
    Function<String, String> normalize = Function.identity();
    for (UnaryOperator<String> step : steps) {
        normalize = normalize.andThen(step);
    }
    IO.println("normalize(\"  My Nice Title \")=" + normalize.apply("  My Nice Title "));

    // 2 - Predicate: and, or, negate, Predicate.not
    Predicate<String> isShort = s -> s.length() <= 4;
    Predicate<String> startsWithP = s -> s.startsWith("P");
    List<String> firstNames = List.of("Paul", "Mélanie", "Jo", "Sébastien", "Pierre");
    IO.println("short and P: " + filter(firstNames, isShort.and(startsWithP)));
    IO.println("short or P: " + filter(firstNames, isShort.or(startsWithP)));
    IO.println("not short: " + filter(firstNames, isShort.negate()));
    IO.println("not empty: " + filter(List.of("a", "", "b"), Predicate.not(String::isEmpty)));

    // 3 - Consumer: andThen verkettet zwei Verarbeitungen desselben Werts
    List<String> log = new ArrayList<>();
    Consumer<String> display = s -> IO.println("display: " + s);
    Consumer<String> remember = log::add;
    Consumer<String> both = display.andThen(remember);
    both.accept("first");
    both.accept("second");
    IO.println("log: " + log);

    // 4 - Comparator: comparing, thenComparing, reversed
    List<Person> persons = new ArrayList<>(List.of(new Person("Paul", 32),
            new Person("Mélanie", 25), new Person("Jo", 32), new Person("Sébastien", 25)));
    persons.sort(Comparator.comparing(Person::age).thenComparing(Person::name));
    IO.println("by age then name: " + persons);
    persons.sort(Comparator.comparingInt(Person::age).reversed()
            .thenComparing(Person::name, Comparator.reverseOrder()));
    IO.println("by descending age then descending name: " + persons);
    // BinaryOperator.minBy erstellt eine Funktion aus einem Comparator
    BinaryOperator<Person> youngest = BinaryOperator.minBy(Comparator.comparingInt(Person::age));
    IO.println("youngest(Paul, Mélanie)=" + youngest.apply(persons.get(0), persons.get(3)));
}

static <T> List<T> filter(List<T> elements, Predicate<? super T> predicate) {
    List<T> result = new ArrayList<>();
    for (T element : elements) {
        if (predicate.test(element)) {
            result.add(element);
        }
    }
    return result;
}

void main() {

    int threshold = 5;

    // ... sofern sie effektiv final sind: threshold = 10; würde abgelehnt
    int otherThreshold = 10;
    Predicate<Integer> exceedsOther = n -> n > otherThreshold;
    IO.println("threshold=" + otherThreshold + " : exceeds(7)=" + exceedsOther.test(7));

    // int total = 0; IntConsumer accumulate = n -> total += n;  // abgelehnt
    // ... aber es kann das Objekt verändern, das sie referenziert
    AtomicInteger total = new AtomicInteger();
    IntConsumer accumulate = n -> total.addAndGet(n);
    accumulate.accept(3);
    accumulate.accept(4);
    IO.println("total=" + total.get());
    // ... oder ein Feld des aktuellen Objekts (das Lambda erfasst this)
    Runnable count = () -> nbCalls++;
    count.run();
    count.run();
    IO.println("nbCalls=" + nbCalls);

    // 3 - ein Closure: Das erfasste Objekt überlebt die Methode, die es erzeugt hat
    IntSupplier counterA = createCounter();
    IntSupplier counterB = createCounter();
    IO.println("A : " + counterA.getAsInt() + " " + counterA.getAsInt() + " " + counterA.getAsInt());
    IO.println("B : " + counterB.getAsInt() + " " + counterB.getAsInt());

    // 4 - die for-Schleife: Die Variable i ändert sich, sie kann nicht erfasst werden
    List<Runnable> actions = new ArrayList<>();
    for (int i = 0; i < 3; i++) {
        // actions.add(() -> IO.print(i + " "));  // abgelehnt: i ist nicht effektiv final
        int copy = i;
        actions.add(() -> IO.print(copy + " "));
    }
    IO.print("for, capture of a copy: ");
    actions.forEach(Runnable::run);
    IO.println();

    actions.clear();
    for (int j : new int[] { 0, 1, 2 }) {
        actions.add(() -> IO.print(j + " "));
    }
    IO.print("for-each: ");
    actions.forEach(Runnable::run);

Um sie zu erzeugen, speichert die virtuelle Maschine die erfassten Werte in Feldern des Objekts, das sie für das Lambda erzeugt;
    • Zeilen 31–34: Jeder Aufruf von [createCounter] erzeugt ein neues [AtomicInteger]-Objekt – und damit einen neuen Zähler –, das von den anderen unabhängig ist. Die Ergebnisse (Zeilen 6–7) bestätigen das;
    • Zeilen 38–42: In einer gewöhnlichen [for]-Schleife wird die Variable [i] bei jedem Durchlauf verändert ([i++]): Sie ist nicht effektiv final, und das Lambda in Zeile 39 würde abgelehnt. Java beseitigt diese Falle zur Kompilierzeit. Die Lösung besteht darin, im Schleifenrumpf eine Variable [copy] zu deklarieren – eine neue pro Durchlauf, die nie verändert wird (Zeile 40) –, sodass jedes Lambda seine eigene erfasst;
    • Zeilen 49–51: Bei der „Für jedes Element“-Schleife [for] tritt das Problem nicht auf: Die Variable [j] ist bei jedem Durchlauf eine neue Variable, wird nie verändert und ist daher effektiv final;
    • Zeilen 44 und 53: Die Methode [forEach] der Collections erwartet einen [Consumer] und führt ihn auf jedem Element aus. Hier ist jedes Element selbst ein *[Runnable]*, und die Referenz **[Runnable::run]*** (jedes Objekt vom Typ *[Runnable]*, auf dem *[run] aufgerufen wird) führt es aus.

    Die Regel zu effektiv finalen Variablen mag restriktiv erscheinen. Sie hat jedoch eine solide Begründung: Ein Lambda kann später oder in einem anderen Thread (Kapitel 8) ausgeführt werden. Könnte es die lokalen Variablen einer Methode verändern, die möglicherweise bereits beendet ist, oder sie lesen, während ein anderer Thread sie verändert, hätten wir es mit schwer vorhersehbarem Verhalten zu tun. Indem Java verlangt, dass Variablen unverändert bleiben, verhindert es diese Situationen; wenn ein gemeinsamer, veränderlicher Zustand wirklich notwendig ist, wird er explizit über ein Objekt abgebildet ([AtomicInteger], Collection …), dessen Verhalten in Bezug auf Threads spezifiziert ist.

Es muss keine Klasse geschrieben werden. Diese Flexibilität erklärt, warum moderne Bibliotheken (die Stream-API, die asynchrone Programmierung in Kapitel 9, Spring) funktionale Schnittstellen intensiv nutzen;
    • eine Schnittstelle mit mehreren Methoden ist dann im Vorteil, wenn das zu implementierende Verhalten mehrere zusammengehörige Operationen umfasst ([calculate] und [name] oben) oder wenn es einen eigenen Zustand und eine eigene Identität benötigt.

    Dies gilt für die Schnittstelle [ITaxDao] in der [dao]-Schicht aus Kapitel 6: Obwohl sie nur eine Methode besitzt, [List<TaxBracket> getTaxBrackets()], haben ihre Implementierungen einen Zustand (die gelesenen Steuerstufen, den Dateinamen), werden vom Dependency-Injection-Container erzeugt und stellen eine klar benannte Rolle innerhalb der Anwendung dar. Ein [Supplier<List<TaxBracket>>] hätte technisch genügt, wäre aber deutlich weniger aussagekräftig gewesen. Funktionale Schnittstellen reservieren wir daher für kurze, einmalige Verhaltensweisen (ein Kriterium, eine Transformation, eine Aktion) und „fachliche“ Schnittstellen für die Rollen der Anwendung, unabhängig von der Anzahl der enthaltenen Methoden.

    7.5. Ereignisbehandlung

    7.5.1. Das Listener-Modell

    Funktionale Schnittstellen dienen dazu, Ereignisse einzurichten. Java besitzt kein eigenes Schlüsselwort für Ereignisse: Es verwendet eine Reihe von Konventionen, das sogenannte „Listener-Modell“, das bereits mit Java 1.1 für grafische Komponenten und JavaBeans eingeführt wurde. Eine Klasse [C1] , die ein Ereignis [Xxx] signalisieren möchte, geht wie folgt vor:

    • Eine Klasse [XxxEvent], abgeleitet von [java.util.EventObject], kapselt die Informationen zum Ereignis. [EventObject] speichert das Objekt, das das Ereignis ausgelöst hat – die sogenannte Quelle –, die über [getSource()] abgerufen wird;
    • eine Schnittstelle [XxxListener], die die leere Schnittstelle [java.util.EventListener] (eine reine Markierung) erweitert, definiert die Methode(n), die beim Eintreten des Ereignisses aufgerufen werden. Mit nur einer Methode ist sie eine funktionale Schnittstelle: Ein Listener kann ein Lambda sein;
    • Die Klasse [C1] verwaltet eine Liste von Listenern und stellt zwei öffentliche Methoden zum An- und Abmelden bereit: [addXxxListener(XxxListener l)] und [removeXxxListener(XxxListener l)];
    • Wenn eine Instanz [c1] der Klasse [C1] das Ereignis signalisieren möchte, erzeugt sie ein Objekt [XxxEvent] und ruft die Methode jedes registrierten Listeners auf, wobei sie ihm dieses Objekt übergibt. Per Konvention übernimmt diese Benachrichtigung eine geschützte Methode [fireXxx(XxxEvent e)] („fire“), die eine abgeleitete Klasse überschreiben kann, um die Veröffentlichung des Ereignisses zu ändern;
    • wenn ein Objekt [c2] über das Ereignis [Xxx] des Objekts [c1] benachrichtigt werden möchte, registriert es sich mit [c1.addXxxListener(...)]. Es kann sich über [c1.removeXxxListener(...)] abmelden, wenn es nicht mehr benachrichtigt werden möchte. Da [c1] eine Liste verwaltet, können sich verschiedene Objekte anmelden, um über dasselbe Ereignis benachrichtigt zu werden.

    In diesem Szenario haben wir:

    • eine Klasse, die ein Ereignis signalisiert (auch „veröffentlicht“ oder „aussendet“);
    • Objekte, die über dieses Ereignis benachrichtigt werden. Man sagt, sie abonnieren das Ereignis bzw. registrieren sich dafür: Dies sind die Listener oder Ereignishandler;
    • eine Listener-Schnittstelle, die die Signatur der Methoden festlegt, die über das Ereignis benachrichtigt werden.

    Dies ist das Entwurfsmuster Observer: Der Sender kennt seine Abonnenten nicht; er benachrichtigt sie lediglich. Dieses Modell bietet denselben Schutz wie ein eigenes Schlüsselwort: Die Liste der Listener ist ein privates Feld des Senders. Von außen kann man sich nur an- oder abmelden; man kann die Liste nicht leeren, andere Listener nicht ersetzen und das Ereignis nicht anstelle des Senders auslösen.

    double getTemperature() {
        return temperature;

    void setTemperature(double temperature) {
        this.temperature = temperature;

            fireTemperatureTooHigh(new TemperatureTooHighEvent(this, temperature));

    void addTemperatureTooHighListener(TemperatureTooHighListener listener) {
        listeners.add(Objects.requireNonNull(listener));

        listeners.remove(listener);

    // Lambdas und die Stream-API

void main() {
    List<Integer> numbers = List.of(3, 8, 1, 6, 5, 4, 9, 2);

    // 1 - filter und map erwarten ein Predicate<T> und eine Function<T, R>
    Predicate<Integer> isEven = n -> n % 2 == 0;
    Function<Integer, Integer> square = n -> n * n;
    List<Integer> evenSquares = numbers.stream().filter(isEven).map(square).toList();
    IO.println("Stream: " + evenSquares);

    // 2 - unsere eigene Filtermethode, aufgerufen mit einem Lambda und dann mit einer Methodenreferenz
    IO.println("filter(n > 4): " + Tools.filter(numbers, n -> n > 4));
    IO.println("filter(isOdd): " + Tools.filter(numbers, Tools::isOdd));

    // 3 - die Ausführung wird verzögert: das Prädikat wird erst von der terminalen Operation aufgerufen
    Stream<Integer> large = numbers.stream().filter(n -> {
        IO.print("[test " + n + "] ");
        return n > 7;
    });
    IO.println("the stream is defined, nothing has been executed yet");
    large.forEach(n -> IO.print("-> " + n + " "));
    IO.println();

    // 4 - unsere eigenen Zwischenoperationen mit Gatherern (Gatherer, Java 24)
    List<String> cities = List.of("Angers", "Paris", "Lyon", "Nantes", "Aix");
    List<String> result = cities.stream()
            .gather(Tools.filter(v -> v.length() <= 5))
            .gather(Tools.transform(String::toUpperCase))
            .toList();
    IO.println("gatherers: " + result);
}

class Tools {
    // filtert eine Liste mit einem Prädikat: die Arbeit, die filter leistet
    static <T> List<T> filter(List<T> source, Predicate<? super T> predicate) {
        List<T> result = new ArrayList<>();
        for (T element : source) {
            if (predicate.test(element)) {
                result.add(element);
            }
        }
        return result;
    }

    static boolean isOdd(int n) {
        return n % 2 != 0;
    }

    // eine Zwischenoperation des Streams, die nur die Elemente durchlässt, die das Prädikat erfüllen
    static <T> Gatherer<T, ?, T> filter(Predicate<? super T> predicate) {
        return Gatherer.of((_, element, downstream) -> !predicate.test(element) || downstream.push(element));
    }

    // eine Zwischenoperation, die jedes Element umwandelt: das Äquivalent von map
    static <T, R> Gatherer<T, ?, R> transform(Function<? super T, ? extends R> transformation) {
        return Gatherer.of((_, element, downstream) -> downstream.push(transformation.apply(element)));
    }
}

    • Zeilen 36–44: unsere Methode [filter]. Sie ist generisch: Sie filtert eine Liste von Elementen beliebigen Typs [T] mithilfe eines Prädikats vom Typ [Predicate<? super T>]. Sie durchläuft die Liste, ruft für jedes Element das Prädikat auf (Zeile 39) und gibt die Liste der ausgewählten Elemente zurück;
    • Zeile 13: Aufruf von [filter] mit einem Lambda. Der Typ [T] wird aus der Liste abgeleitet: [Integer]. Zeile 14: Ihr wird eine Methodenreferenz übergeben: [isOdd] (Zeile 46) erhält einen [int]; der Compiler fügt die Umwandlung aus [Integer] hinzu;
    • Zeilen 17–20: ein ausführliches Prädikat, das jedes Element anzeigt, das es prüft. Das Ergebnis (Zeilen 5–6) zeigt, dass die Definition des Flusses nichts ausführt: Die Meldung in Zeile 21 wird vor dem ersten Test angezeigt. Erst wenn die terminale Operation [forEach] (Zeile 22) die Elemente anfordert, wird das Prädikat ausgeführt, und die Tests wechseln sich mit den Ausgaben von [forEach] ab: Jedes Element durchläuft den gesamten Fluss, bevor das nächste in ihn eintritt. Dies ist die verzögerte (oder „lazy“) Ausführung der Streams. Unsere Methode [filter] dagegen erstellt die gesamte Ergebnisliste, bevor sie sie zurückgibt;
    • Zeilen 51–58: Um eigene Zwischenoperationen zu schreiben – die wie die der Stream-API lazy sind –, verwenden wir die Zwischen-Collector ([Gatherer], Java 24), die für Zwischenoperationen das Gegenstück zu den Collectors ([Collector]) sind, die von [collect] verwendet werden. [Gatherer.of] erhält ein Lambda mit drei Parametern, das für jedes Element des Streams aufgerufen wird: einen Zustand (hier unnötig, daher der anonyme Parameter [_]), das Element und die nächste Stufe des Flusses ([downstream]), an die ein Element über [downstream.push(...)] weitergegeben wird. Das Lambda gibt [false] zurück, um den Stream anzuhalten; unsere Funktionen entscheiden das nie selbst: Sie geben das Ergebnis von [push] zurück, das nur dann [false] ist, wenn die nachgelagerte Stufe keine Elemente mehr haben möchte (oder [true] , wenn der Filter ein Element verwirft). Der Filter (Zeile 52) leitet nur die Elemente weiter, die das Prädikat erfüllen; die Transformation (Zeile 57) leitet das Ergebnis der auf jedes Element angewendeten Funktion weiter;
    • Zeile 56: [transform] ist doppelt generisch: [T] ist der Typ der empfangenen Elemente und [R] der Typ der erzeugten Elemente. Der Parameter [Function<? super T, ? extends R>] folgt der Regel, der wir bereits begegnet sind: Die Funktion konsumiert [T] und erzeugt [R];
    • Zeilen 27–30: Die Stream-Methode [gather] fügt unsere Operationen in die Kette ein, die genauso geschrieben wird wie für die Operationen der Stream-API: Wir behalten Städte mit bis zu 5 Buchstaben und schreiben sie dann groß.

    Die gesamte Stream-API ist nach diesem Modell aufgebaut: Operationen, die funktionale Schnittstellen entgegennehmen und neue Streams erzeugen, deren Elemente erst auf Anforderung der terminalen Operation berechnet werden.

    7.7. Ausdrucksbäume

    Einige Sprachen wie C# erlauben es, ein Lambda nicht in ausführbaren Code, sondern in eine Datenstruktur umzuwandeln, die es beschreibt (ein „Ausdrucksbaum“): Ein Programm kann dann das Lambda [t -> t.getLimit() > 20000] analysieren und beispielsweise in eine SQL-Klausel [WHERE limits > 20000] übersetzen, die vom Datenbankserver ausgeführt wird.

    Java hat kein Äquivalent. Ein Java-Lambda wird immer in ausführbaren Code kompiliert: Man kann es aufrufen, aber nicht untersuchen, was es tut. Bibliotheken für den Datenbankzugriff verwenden daher andere Mittel, um eine Abfrage auszudrücken. Hibernate, das wir in Kapitel 11 behandeln, bietet zwei Lösungen: eine SQL-ähnliche Abfragesprache, die in Klassen und Eigenschaften formuliert ist, HQL (["from Bracket t where t.limit > 20000"]), und die Criteria-API von Jakarta Persistence, die die Abfrage durch Methodenaufrufe aufbaut ([cb.gt(t.get("limit"), 20000)]). In beiden Fällen ist die Abfrage ein Datenobjekt (eine Zeichenkette oder ein Objektbaum), das Hibernate in SQL übersetzt, während ein an [filter] übergebenes Lambda innerhalb des Java-Programms ausgeführt wird.

    7.8. Fazit

    Die wichtigsten Punkte dieses Kapitels:

    • Eine funktionale Schnittstelle ist eine Schnittstelle mit nur einer abstrakten Methode. Die vordefinierten Schnittstellen des Pakets [java.util.function] ([Function], [Supplier], [Consumer], [Predicate], ihre Varianten mit zwei Parametern und ihre primitiven Versionen) sowie [Runnable], [Callable] und [Comparator] machen es in der Regel überflüssig, eigene zu definieren; wird dennoch eine definiert, wird sie mit [@FunctionalInterface] annotiert;
    • Eine funktionale Schnittstelle kann durch eine Klasse (benannt oder anonym), durch einen Lambda-Ausdruck oder durch eine Methodenreferenz implementiert werden ([Class::staticMethod], [object::method], [Class::instanceMethod], [Class::new]). Ein Lambda hat keinen eigenen Typ: Der Zieltyp bestimmt ihn;
    • Lambdas erfassen die sie umgebenden lokalen Variablen, sofern diese Variablen effektiv final sind; veränderlicher Zustand wird über ein Objekt oder ein Feld abgebildet;
    • die Methoden [andThen], [compose], [and], [negate], [comparing], [thenComparing] … bilden aus vorhandenen Funktionen neue;
    • In Java ist ein Lambda eine Instanz einer Schnittstelle: Für kurze, einmalige Verhaltensweisen wählt man eine funktionale Schnittstelle, für eine Rolle der Anwendung dagegen eine Schnittstelle mit mehreren Methoden (oder eine „fachliche“ Schnittstelle);
    • Ein Ereignis wird mit dem Listener-Muster eingerichtet: eine Klasse [XxxEvent] , abgeleitet von [EventObject], eine Schnittstelle [XxxListener], die Methoden [addXxxListener] / [removeXxxListener], und eine Liste von Listenern ([CopyOnWriteArrayList]), die von einer Methode [fireXxx] durchlaufen wird. Um einen Listener abzumelden, muss man das angemeldete Objekt aufbewahren. [PropertyChangeSupport] stellt diesen Mechanismus für Eigenschaftsänderungen fertig bereit;
    • die Stream-API basiert auf Operationen, die funktionale Schnittstellen akzeptieren; Java kennt keine Ausdrucksbäume, und Hibernate formuliert seine Abfragen in HQL oder mit der Criteria-API.

    Lambdas werden in allen folgenden Kapiteln wieder auftauchen: Ein Thread führt ein [Runnable] aus, und ein [ExecutorService] führt ein [Callable] aus (Kapitel 8), ein [CompletableFuture] verkettet Funktionen (Kapitel 9), und Spring-Boot-Webdienste verarbeiten HTTP-Anfragen in Methoden, die das Framework als Listener aufruft (Kapitel 13).

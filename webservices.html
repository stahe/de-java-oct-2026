    13.1. Einführung

    Im vorherigen Kapitel haben wir mehrere TCP/IP-Client-Server-Anwendungen vorgestellt. Da Clients und Server Textzeilen austauschen, können sie in jeder Sprache geschrieben werden. Der Client muss lediglich das vom Server erwartete Kommunikationsprotokoll kennen.

    Webservices sind ebenfalls Serveranwendungen (TCP/IP). Sie haben die folgenden Merkmale:

    • Sie werden von Webservern gehostet, und das Austauschprotokoll zwischen Client und Server ist HTTP (HyperText Transfer Protocol), ein auf TCP/IP aufbauendes Protokoll, das wir im vorherigen Kapitel untersucht haben;
    • Der Webservice hat ein standardisiertes Kommunikationsprotokoll, unabhängig vom angebotenen Dienst. Ein Webservice bietet verschiedene Dienste an: S1, S2 …, Sn. Jeder dieser Dienste erwartet vom Client bereitgestellte Parameter und liefert dem Client ein Ergebnis. Für jeden Dienst muss der Client wissen:
      • wie der Dienst Si anzugeben ist;
      • die Liste der bereitzustellenden Parameter und ihre Typen;
      • den Typ des vom Dienst gelieferten Ergebnisses. Sobald diese Elemente bekannt sind, folgt der Dialog zwischen Client und Server demselben Schema, unabhängig davon, welcher Webservice abgefragt wird. Der Client-Code ist somit standardisiert;
    • Um sich vor Angriffen aus dem Internet zu schützen, öffnen viele Organisationen auf ihren Servern nur bestimmte Ports nach außen: vor allem die Ports 80 (HTTP) und 443 (HTTPS) für den Webservice. Alle anderen Ports sind gesperrt. Folglich sind Client-Server-Anwendungen wie die im vorherigen Kapitel beschriebenen im Allgemeinen auf das private Netzwerk (Intranet) der Organisation beschränkt. Das Hosten eines Dienstes auf einem Webserver macht ihn für die gesamte Internet-Gemeinschaft zugänglich;
    • Der Webservice lässt sich als entferntes Objekt betrachten: Die von ihm angebotenen Dienste werden dann zu Methoden dieses Objekts. Ein Client kann dieses entfernte Objekt über ein Zwischenobjekt, einen sogenannten Proxy, der die gesamte Netzwerkkommunikation verbirgt, so verwenden, als wäre es lokal. So lässt sich ein Client bauen, der von dieser Schicht unabhängig ist: Ändert sich die Schicht, muss der Rest des Clients nicht angepasst werden;
    • Wie bei den TCP/IP-Client-Server-Anwendungen aus dem vorherigen Kapitel können Client und Server in jeder Programmiersprache geschrieben werden. Sie tauschen Textzeilen aus, die aus zwei Teilen bestehen: den vom HTTP-Protokoll verlangten Headern und dem Nachrichtentext, dessen Format zwischen Client und Server vereinbart wird.

    13.1.1. Gestern: SOAP und WSDL

    In den 2000er-Jahren folgten Webservices meist dem Standard SOAP (Simple Object Access Protocol). Der Client sendete eine HTTP-Anfrage per POST, deren Rumpf ein XML-Dokument war: ein „Umschlag“ mit dem Namen der aufgerufenen Methode und ihren Parametern. Der Server antwortete mit einem weiteren XML-Umschlag, der das Ergebnis enthielt. Jeder Dienst wurde durch ein XML-Dokument im Format WSDL (Web Services Description Language) beschrieben, das unter der URL des Dienstes gefolgt von [?wsdl] abrufbar war: Es listete die Methoden, ihre Parameter und ihre Typen auf. Anhand dieses Dokuments erzeugten Werkzeuge automatisch den Proxy des Dienstes.

    In Java wurden diese Dienste mit der API JAX-WS geschrieben: Eine mit [@WebService] annotierte Klasse, deren öffentliche Methoden (die mit [@WebMethod] annotiert sein konnten) zu den Methoden des Dienstes wurden; das Werkzeug [wsimport] erzeugte den Client-Proxy aus der WSDL. JAX-WS war von Java 6 bis Java 10 Teil des JDK; in Java 11 wurde es entfernt (JEP 320) und existiert heute außerhalb des JDK unter dem Namen Jakarta XML Web Services. Es findet sich noch in Altanwendungen, doch neue Dienste verwenden es selten. Zu den Gründen für diese Ablösung zählen die Schwerfälligkeit von XML und SOAP-Umschlägen, die Komplexität der zugehörigen Standards (WS-Security, WS-Addressing usw.) und die Schwierigkeit, diese Dienste aus einem Browser aufzurufen.

    13.1.2. Heute: REST und JSON

    Die meisten aktuellen Webservices folgen dem Stil REST (REpresentational State Transfer) und tauschen JSON-Dokumente aus (JavaScript Object Notation, vorgestellt in Kapitel 5). Der REST-Stil beruht auf den folgenden Prinzipien:

    • Der Service stellt Ressourcen bereit, die jeweils durch eine URL bezeichnet werden: [/tax], [/clients/12], [/clients/12/orders];
    • Auf diese Ressourcen wird mit den Methoden (auch Verben genannt) des HTTP-Protokolls zugegriffen, von denen jede eine bestimmte Bedeutung hat;
    • Das Ergebnis der Aktion wird durch den HTTP-Statuscode in der Antwort angezeigt;
    • Der Rumpf von Anfragen und Antworten ist meist ein JSON-Dokument, das kompakter und einfacher als XML ist;
    • Der Service ist zustandslos: Jede Anfrage enthält alle für ihre Verarbeitung nötigen Informationen; der Server speichert von einer Anfrage zur nächsten keine Informationen über einen bestimmten Client.

    Ein REST-Service hat kein zwingend vorgeschriebenes Äquivalent zu WSDL. Üblich ist es jedoch, ihn mit einem OpenAPI-Dokument (früher Swagger) im JSON- oder YAML-Format zu beschreiben, aus dem Werkzeuge Dokumentation, Testseiten und Clients erzeugen können. Darauf kommen wir später zurück.

    Erwähnen wir schließlich gRPC, von Google entworfen: Die Methoden des Dienstes und ihre Nachrichten werden in einer [.proto]-Datei beschrieben, aus der Werkzeuge Server und Client erzeugen, so wie zur Zeit von WSDL; die Nachrichten werden in einem kompakten Binärformat (Protocol Buffers) kodiert und über HTTP/2 übertragen. gRPC ist sehr effizient und beliebt für die Kommunikation zwischen Diensten innerhalb derselben Organisation, eignet sich aber schlecht für Browser. Es ist in Java mit der Bibliothek [grpc-java] verfügbar, die wir nicht verwenden werden.

    13.1.3. Spring Boot und Spring MVC

    Zum Schreiben unserer Webservices verwenden wir Spring Boot. In Kapitel 6 haben wir den Dependency-Injection-Container des Spring Frameworks verwendet. Dieses Framework enthält auch ein Webmodul, Spring MVC, das mithilfe von Annotationen eine URL und eine HTTP-Methode einer Java-Methode zuordnet: [@RestController] an der Klasse, [@GetMapping], [@PostMapping] … an ihren Methoden. Spring Boot (Version 1.0 im Jahr 2014, Version 4 im November 2025, mit Spring Framework 7) vereinfacht den Einsatz von Spring:

    • Es konfiguriert die Anwendung automatisch anhand der verfügbaren Bibliotheken: Sind Spring MVC und Jackson vorhanden, richtet es alles ein, was für einen JSON-Webservice nötig ist, ohne eine einzige Konfigurationszeile;
    • Es bettet den Webserver ein in die Anwendung: Der Server Tomcat (Version 11) ist einfach eine Bibliothek, die vom Hauptprogramm gestartet wird. Es ist daher nicht nötig, einen separaten Webserver oder Anwendungsserver (Tomcat, GlassFish, WildFly …) zu installieren, auf dem die Anwendung früher als [.war]-Archiv bereitgestellt wurde;
    • Es stellt Starter bereit – Maven-Abhängigkeiten, die alles bündeln, was für einen bestimmten Anwendungsfall nötig ist. Der Starter [spring-boot-starter-webmvc] enthält Spring MVC, Tomcat, Jackson 3 (Kapitel 5) und Logging (SLF4J und Logback);
    • Es stellt ein übergeordnetes Maven-Projekt bereit, [spring-boot-starter-parent], das die Versionen all dieser untereinander kompatiblen Bibliotheken festlegt, sowie ein Maven-Plugin, [spring-boot-maven-plugin], das die Anwendung startet ([mvn spring-boot:run]) und sie als einzelne ausführbare Datei, [.jar], paketiert.

    Spring Boot ist nicht die einzige Lösung: Jakarta EE (früher Java EE) definiert den API-Standard JAX-RS (Jakarta RESTful Web Services), und auch Frameworks wie Quarkus, Micronaut und Helidon sind weit verbreitet. Spring Boot ist jedoch am weitesten verbreitet und baut ganz natürlich auf dem auf, was wir in Kapitel 6 behandelt haben.

    Erläuterungen:

    • Zeile 8: Die Annotation [@RestController] kennzeichnet die Klasse als Controller: Spring erzeugt beim Start eine einzige Instanz davon (einen Singleton) und weist ihr die HTTP-Anfragen zu, bei denen die URL einer ihrer Methoden entspricht. Das Ergebnis jeder Methode wird unverändert im Rumpf der Antwort an den Client gesendet;
    • Zeilen 12–15: Die Annotation [@GetMapping("/")] ordnet die HTTP-Methode GET der URL [/] (dem Wurzelverzeichnis der Website) und der Methode [home] zu, die einen Text mit Erläuterungen zur Verwendung des Dienstes zurückgibt;
    • Zeilen 20–23: Die Template-URL (die sogenannte Route) [/hello/{name}] enthält eine Variable [{name}]: Sie entspricht jedem URL-Segment, das nach [/hello/] folgt. Somit weist die URL [/hello/Carla%20Bruni] den Wert [Carla Bruni] der Variablen [{name}] zu (der Code [%20] steht in einer URL für ein Leerzeichen). Die Annotation [@PathVariable] (Zeile 21) weist Spring an, diesen Wert an den gleichnamigen Methodenparameter zu übergeben: Das ist Datenbindung. import java.io.IOException;
import java.net.ConnectException;
import java.net.URI;
import java.net.URLEncoder;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.nio.charset.StandardCharsets;
import tools.jackson.databind.json.JsonMapper;

// Konsolenclient des Webdienstes WsHello
public class Main {

    // die JSON-Antwort des Dienstes: dieselben Komponentennamen wie auf der Serverseite
    record Greeting(String name, String message) {
    }

    public static void main(String[] args) throws InterruptedException {
        // die URL des Dienstes kann als Argument übergeben werden
        URI serviceUrl = URI.create(args.length > 0 ? args[0] : "http://localhost:5100/");
        // der Jackson-Konverter JSON <-> Objekte
        JsonMapper mapper = JsonMapper.builder().build();

        // ein einziger HTTP-Client für die gesamte Dauer des Programms
        try (HttpClient client = HttpClient.newHttpClient()) {
            while (true) {
                // der Name der Dame
                String input = IO.readln("Name of the lady (nothing to stop): ");
                String name = input == null ? "" : input.strip();
                if (name.isEmpty()) {
                    break;
                }
                try {
                    // der Name wird in den Pfad der URL eingefügt: er muss darin kodiert werden
                    String encodedName = URLEncoder.encode(name, StandardCharsets.UTF_8).replace("+", "%20");
                    // 1 - Textantwort
                    String text = get(client, serviceUrl.resolve("hello/" + encodedName));
                    IO.println("[text] " + text);
                    // 2 - JSON-Antwort, in ein Greeting-Objekt deserialisiert
                    String json = get(client, serviceUrl.resolve("greeting/" + encodedName));
                    Greeting greeting = mapper.readValue(json, Greeting.class);
                    IO.println("[JSON] " + greeting);
                } catch (ConnectException e) {
                    // unter dieser Adresse lauscht kein Dienst (die Exception hat keine Meldung)
                    IO.println("Error: ConnectException: connection refused (" + serviceUrl + ")");
                } catch (IOException e) {
                    // der Dienst hat mit einem Fehler geantwortet oder die Kommunikation ist fehlgeschlagen
                    IO.println("Error: " + e.getClass().getSimpleName() + " : " + e.getMessage());
                }
            }
        }
    }

    // eine GET-Anfrage, deren Antworttext als Zeichenkette zurückgegeben wird
    private static String get(HttpClient client, URI url) throws IOException, InterruptedException {
        HttpRequest request = HttpRequest.newBuilder(url).GET().build();
        HttpResponse<String> response = client.send(request, HttpResponse.BodyHandlers.ofString());
        // ein anderer Statuscode als 2xx ist ein Fehler
        if (response.statusCode() / 100 != 2) {
            throw new IOException("the service responded " + response.statusCode() + " for " + url);
        }
        return response.body();
    }

    package wsoperations;

import java.util.LinkedHashMap;
import java.util.List;
import java.util.Locale;
import java.util.Map;
import java.util.function.DoubleBinaryOperator;
import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

// der Webdienst WsOperations: die vier Grundrechenarten
@RestController
public class OperationsController {

    // GET /add?a=1.5&b=2 (ebenso für subtract, multiply, divide)
    // [operation] stammt aus dem Pfad der URL, [a] und [b] aus ihrem Query-String
    @GetMapping("/{operation}")
    public ResponseEntity<?> calculateGet(@PathVariable String operation,
            @RequestParam(required = false) String a, @RequestParam(required = false) String b) {
        return calculate(operation, readNumber(a), readNumber(b));
    }

    // POST /calculation mit einem JSON-Body: {"operation":"add","a":1.5,"b":2}
    // der JSON-Body wird in den Parameter [request] deserialisiert
    @PostMapping("/calculation")
    public ResponseEntity<?> calculatePost(@RequestBody CalculationRequest request) {
        return calculate(request.operation(), request.a(), request.b());
    }

    // eine mit Dezimalpunkt geschriebene Zahl, null, wenn sie fehlt oder fehlerhaft ist
    private static Double readNumber(String text) {
        if (text == null) {
            return null;
        }
        try {
            double number = Double.parseDouble(text);
            // NaN und Unendlich werden abgelehnt
            return Double.isFinite(number) ? number : null;
        } catch (NumberFormatException e) {
            return null;
        }
    }

    // die beiden HTTP-Methoden gemeinsame Berechnung
    private static ResponseEntity<?> calculate(String operation, Double a, Double b) {
        // die angeforderte Operation, null, wenn sie unbekannt ist
        String name = operation == null ? "" : operation.toLowerCase(Locale.ROOT);
        DoubleBinaryOperator calculation = switch (name) {
            case "add" -> (x, y) -> x + y;
            case "subtract" -> (x, y) -> x - y;
            case "multiply" -> (x, y) -> x * y;
            case "divide" -> (x, y) -> x / y;
            default -> null;
        };
        // Prüfung der Parameter: die Fehler werden gesammelt
        Map<String, List<String>> errors = new LinkedHashMap<>();
        if (calculation == null) {
            errors.put("operation", List.of("Unknown operation [" + name
                    + "]: use add, subtract, multiply or divide"));
        }
        if (a == null) {
            errors.put("a", List.of("The number a is missing or incorrect"));
        }
        if (b == null) {
            errors.put("b", List.of("The number b is missing or incorrect"));
        }
        if (!errors.isEmpty()) {
            // Antwort 400 mit der Liste der Fehler
            ProblemDetail problem = ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
            problem.setTitle("Incorrect parameters");
            problem.setProperty("errors", errors);
            return ResponseEntity.badRequest().body(problem);

        return ResponseEntity.ok(new CalculationResult(name, a, b, calculation.applyAsDouble(a, b)));
    }

    • Zeilen 24–28: Die GET-Anfrage. Der Parameter [operation] der Methode ist an die Routenvariable [{operation}] ([@PathVariable]) gebunden. Die Parameter [a] und [b], die mit [@RequestParam] annotiert sind, werden an die gleichnamigen Parameter im Query-String ([?a=1.5&b=2]) gebunden. Sie sind optional ([required = false]): Ein fehlender Parameter wird als [null] behandelt; andernfalls würde Spring eine Anfrage, in der einer von ihnen fehlt, mit einer 400-Antwort ablehnen;
    • Zeile 26: [a] und [b] sind als Typ [String] deklariert. Wir hätten sie auch als Typ [double] oder [Double] deklarieren können: Spring hätte dann die Konvertierung selbst durchgeführt und einen fehlerhaften Wert mit einer 400-Antwort mit einer generischen Fehlermeldung abgelehnt. Indem wir sie als Zeichenketten empfangen, behalten wir die Kontrolle über die Fehlermeldungen;
    • Zeilen 32–35: die POST-Anfrage. Der Parameter [request], der mit [@RequestBody] annotiert ist, wird von Jackson aus dem JSON-Body der Anfrage erstellt. Seine Komponenten haben den Typ [Double] (Zeile 93) und nicht [double]: Eine im JSON-Dokument fehlende Eigenschaft wird dann als [null] ausgewertet, wodurch sie erkannt werden kann;
    • Zeilen 38–49: Umwandlung einer Zeichenkette in eine Zahl; schlägt sie fehl, ist das Ergebnis [null]. Sowohl in der URL als auch in JSON werden Zahlen mit Dezimalpunkt geschrieben: [Double.parseDouble], das von der Systemsprache unabhängig ist, ist daher das richtige Werkzeug (und nicht [NumberFormat], das auf einem französischen Server ein Komma erwarten würde, siehe Kapitel 5). Es akzeptiert außerdem die Texte [NaN] und [Infinity], die wir ablehnen (Zeile 45);
    • Zeile 54: der Name der Operation in Kleinbuchstaben. [Locale.ROOT] führt die Umwandlung unabhängig von der Systemsprache durch;
    • Zeilen 55–61: Die angeforderte Operation wird durch ein funktionales Interface (Kapitel 7) dargestellt, [DoubleBinaryOperator], dessen Methode [applyAsDouble(double, double)] einen [double] zurückgibt. Ein [switch]-Ausdruck wählt das zur Operation passende Lambda aus; bei einer unbekannten Operation wählt er [null] aus;
    • Zeilen 63–73: Die drei Parameter werden validiert, indem die Fehler in einem Dictionary gesammelt werden, das jedem Parameter die Liste seiner Fehlermeldungen zuordnet. Eine [LinkedHashMap] behält die Einfügereihenfolge bei;
    • Zeilen 74–80: Wird ein Fehler gefunden, wird eine 400-Antwort zurückgegeben. Die Spring-Klasse [ProblemDetail] stellt ein „Problem Details“-Dokument dar: [forStatus] erstellt es mit einem Statuscode, [setTitle] legt seinen Titel fest, und [setProperty] fügt ihm eine Eigenschaft hinzu, hier [errors], die Liste der Fehler. Die Klasse [ResponseEntity] stellt eine vollständige HTTP-Antwort dar: Statuscode, Header und Body. [ResponseEntity.badRequest()] bereitet eine 400-Antwort vor, und [body] liefert ihren Body;
    • Zeilen 82–87: Eine Division durch null wird mit einer 400-Antwort abgelehnt, deren Dokument diesmal ein Detail enthält ([forStatusAndDetail]). Diese Ablehnung ist notwendig: In Java löst die Division eines [double] durch null keine Exception aus, sondern liefert unendlich ([Double.POSITIVE_INFINITY]), was ein JSON-Dokument nicht darstellen kann (Jackson würde es als Zeichenkette schreiben, ["Infinity"]). Der Test [b == 0] vergleicht den Wert des [Double]-Objekts mit null: Java „entpackt“ es automatisch (Unboxing);
    • Zeile 89: die 200-Antwort, deren Body das als JSON serialisierte Objekt [CalculationResult] ist;
    • Zeilen 93–98: die beiden mit den Clients ausgetauschten Typen. Diese Objekte, die ausschließlich dazu dienen, Daten zwischen zwei Anwendungen zu transportieren, heißen DTO (Data Transfer Object). Records eignen sich dafür ideal.

    Beide Methoden des Controllers geben den Typ [ResponseEntity<?>] zurück: eine Antwort, deren Body von beliebigem Typ sein kann, hier ein [CalculationResult] oder ein [ProblemDetail]. Spring untersucht den tatsächlichen Typ des Bodys, um ihn zu serialisieren; es weist dem Dokument den Typ [application/json] oder, bei einem [application/problem+json] [ProblemDetail], den Typ zu.

public class Main {

    // die mit dem Dienst ausgetauschten Objekte (die Komponentennamen sind die des JSON)
    record CalculationRequest(String operation, double a, double b) {
    }

    record CalculationResult(String operation, double a, double b, double result) {
    }

    record Problem(String title, String detail, Integer status, Map<String, List<String>> errors) {
    }

    // die Zahlen werden in der aktuellen Kultur eingegeben und angezeigt (fr-FR: Dezimalkomma, en-US: Dezimalpunkt)
    private static final NumberFormat FORMAT = NumberFormat.getInstance();

    public static void main(String[] args) throws InterruptedException {
        URI serviceUrl = URI.create(args.length > 0 ? args[0] : "http://localhost:5110/");
        // der JSON-Konverter; Jackson 3 ignoriert die unbekannten JSON-Eigenschaften (instance...)
        JsonMapper mapper = JsonMapper.builder().build();

        try (HttpClient client = HttpClient.newHttpClient()) {
            while (true) {
                // Eingabe der Operation und der beiden Zahlen (Dezimaltrennzeichen der aktuellen Kultur)
                String input = IO.readln("Operation a b (e.g.: add 1.5 2), nothing to stop: ");
                String[] fields = input == null ? new String[0] : input.strip().split("\\s+");
                if (fields.length == 0 || fields[0].isEmpty()) {
                    break;
                }
                if (fields.length != 3) {
                    IO.println("Three elements are needed: operation a b");
                    continue;
                }
                // lokale Prüfung der beiden Zahlen, vor jedem Aufruf des Dienstes
                String operation = fields[0];
                Double a = readNumber(fields[1]);
                if (a == null) {
                    IO.println("Incorrect number a...");
                }
                Double b = readNumber(fields[2]);
                if (b == null) {
                    IO.println("Incorrect number b...");
                }
                if (a == null || b == null) {
                    continue;
                }
                String calculation = operation + "(" + FORMAT.format(a) + " ; " + FORMAT.format(b) + ")";

                // 1 - GET-Anfrage: in der URL werden die Zahlen mit Dezimalpunkt geschrieben
                String url = URLEncoder.encode(operation, StandardCharsets.UTF_8) + "?a=" + a + "&b=" + b;
                try {
                    HttpRequest request = HttpRequest.newBuilder(serviceUrl.resolve(url)).GET().build();
                    HttpResponse<String> response = client.send(request, BodyHandlers.ofString());
                    if (response.statusCode() == 200) {
                        CalculationResult result = mapper.readValue(response.body(), CalculationResult.class);
                        IO.println("[GET " + url + "] " + calculation
                                + " = " + FORMAT.format(result.result()));
                    } else {
                        // Fehlschlag: der Statuscode und das empfangene Dokument werden unverändert angezeigt
                        IO.println("[GET " + url + "] error " + response.statusCode()
                                + " : " + response.body());
                    }
                } catch (IOException e) {
                    // der Dienst ist nicht erreichbar
                    IO.println("[GET " + url + "] error: " + e);
                }

                // 2 - POST-Anfrage: die Anfrage wird in JSON im Body der Anfrage gesendet
                try {
                    String json = mapper.writeValueAsString(new CalculationRequest(operation, a, b));
                    HttpRequest request = HttpRequest.newBuilder(serviceUrl.resolve("calculation"))
                            .header("Content-Type", "application/json")
                            .POST(HttpRequest.BodyPublishers.ofString(json))
                            .build();
                    HttpResponse<String> response = client.send(request, BodyHandlers.ofString());
                    if (response.statusCode() == 200) {
                        // Erfolg: der Body enthält das Ergebnis
                        CalculationResult result = mapper.readValue(response.body(), CalculationResult.class);
                        IO.println("[POST calculation] " + calculation + " = " + FORMAT.format(result.result()));
                    } else {
                        // Fehlschlag: der Body enthält die Beschreibung des Problems
                        Problem problem = mapper.readValue(response.body(), Problem.class);
                        IO.println("[POST calculation] error " + response.statusCode() + " : " + problem.title());
                        if (problem.detail() != null) {
                            IO.println("  " + problem.detail());
                        }
                        if (problem.errors() != null) {
                            problem.errors().forEach((parameter, messages) ->
                                    IO.println("  " + parameter + " : " + String.join(" ; ", messages)));
                        }
                    }
                } catch (IOException e) {
                    // der Dienst ist nicht erreichbar
                    IO.println("[POST calculation] error: " + e);
                }
            }
        }
    }

    // eine in der aktuellen Kultur eingegebene Zahl, null, wenn die Eingabe keine ist
    private static Double readNumber(String text) {
        ParsePosition position = new ParsePosition(0);
        Number number = FORMAT.parse(text, position);
        // die Eingabe muss vollständig gelesen worden sein: "2.5x" wird abgelehnt
        return number == null || position.getIndex() != text.length() ? null : number.doubleValue();
    }

        if (married != null && children != null && children >= 0 && salary != null && salary >= 0) {
            int tax = business.calculateTax(married, children, salary);
            log.info("Tax(married={}, children={}, salary={}) = {}", married, children, salary, tax);
            return new TaxResponse(tax);

    }

    @Override
    public int calculateTax(boolean married, int nbChildren, int salary) {
        // die Anfrage POST /tax, mit der Anfrage in JSON in ihrem Body
        String json = mapper.writeValueAsString(new TaxRequest(married, nbChildren, salary));
        HttpRequest request = HttpRequest.newBuilder(taxUrl)
                .header("Content-Type", "application/json")
                .POST(HttpRequest.BodyPublishers.ofString(json))
                .build();
        HttpResponse<String> response;
        try {
            // synchrones Senden: die Methode wartet auf die Antwort
            response = client.send(request, HttpResponse.BodyHandlers.ofString());
        } catch (IOException e) {
            // der Dienst ist nicht erreichbar
            throw new TaxException("The web service " + taxUrl + " is unreachable", e);
        } catch (InterruptedException e) {
            // der Thread wurde während des Wartens unterbrochen: dies wird erneut signalisiert
            Thread.currentThread().interrupt();
            throw new TaxException("The tax calculation was interrupted", e);
        }
        // hat der Dienst die Anfrage akzeptiert?
        if (response.statusCode() != 200) {
            throw new TaxException("The web service responded " + response.statusCode()
                    + " : " + response.body(), response.statusCode());
        }
        // die JSON-Antwort {"tax":4282}
        return mapper.readValue(response.body(), TaxResponse.class).tax();
    }
}

    13.7. Zusätzliche Informationen

    13.7.1. Antworttypen und Fehlerbehandlung

    Der Service [WsOperations] gibt Objekte vom Typ [ResponseEntity<?>] zurück: Allein anhand der Signaturen seiner Methoden ist unklar, welche Antworten sie erzeugen können, und der Compiler führt keine Prüfungen durch. Der Service [WsTax] gibt bei Erfolg den spezifischen Typ seiner Antwort zurück, [TaxResponse], und meldet Fehler über Ausnahmen, die von einem [@ExceptionHandler]-Handler in Antworten umgewandelt werden. Das ist bei Spring der gängigste Ansatz: Der Code der Methode behandelt nur den Normalfall, und die Werkzeuge (insbesondere der Generator für OpenAPI-Dokumente) kennen das JSON-Schema der Antwort, ohne dass man es ihnen ausdrücklich mitteilen muss. Ein Unit-Test kann außerdem direkt eine Controller-Methode aufrufen und ihr Ergebnis untersuchen, ohne über HTTP zu gehen. [ResponseEntity<T>] mit einem spezifischen Typ bleibt nützlich, wenn man den Statuscode wählen oder Header hinzufügen muss, zum Beispiel bei einer Antwort 201 (Created) mit ihrem Header [Location]: [ResponseEntity.created(uri).body(client)].

    Ein in einem Controller platzierter [@ExceptionHandler]-Handler behandelt nur die Ausnahmen dieses Controllers. Um die Ausnahmen aller Controller einer Anwendung zu behandeln, platziert man die Handler in einer Klasse, die mit [@RestControllerAdvice] annotiert ist. Spring bietet außerdem die Klasse [ErrorResponseException], eine Ausnahme, die direkt ein [ProblemDetail] mitführt und die entsprechende Antwort ohne Handler erzeugt, sowie die Klasse [ResponseEntityExceptionHandler], die erweitert werden kann, um die Antworten auf Fehler anzupassen, die Spring MVC selbst erkennt (nicht lesbares JSON-Dokument, ungültiger Dokumenttyp usw.).

    13.7.2. Ein gemeinsames Präfix für Routen

    Wenn mehrere Routen ein Präfix gemeinsam haben, wird es einmalig mit der Annotation [@RequestMapping] angegeben, die auf der Controller-Klasse steht. Mit [@RequestMapping("/api/operations")] auf der Klasse [OperationsController] lauten die Routen zum Beispiel [GET /api/operations/add?a=1&b=2] and [POST /api/operations/calculation], ohne weitere Änderungen. Das ist auch eine einfache Möglichkeit, Versionen eines Service zu verwalten ([/api/v1/...], [/api/v2/...]).

    13.7.3. Interceptoren und Validierung

    Unsere Services validieren ihre Parameter selbst. Spring bietet zwei Mechanismen, um diesen Code aus den Controllern auszulagern:

    • Interceptoren: Eine Klasse, die die Schnittstelle [HandlerInterceptor] implementiert und über die Methode [addInterceptors] von [WebMvcConfigurer] registriert wird, wird vor und nach den Controller-Methoden ausgeführt; sie kann die Anfrage untersuchen und selbstständig antworten, ohne den Controller aufzurufen. Sie dienen unter anderem dem Logging, der Messung von Antwortzeiten und der Authentifizierung. Servlet-Filter ([jakarta.servlet.Filter]) erfüllen auf niedrigerer Ebene denselben Zweck;
    • Validierung: Mit dem Starter [spring-boot-starter-validation] (der Hibernate Validator bereitstellt, die Referenzimplementierung der Jakarta-Validation-API) können Komponenten eines DTO mit Constraints annotiert werden: [record TaxRequest(@NotNull Boolean married, @NotNull @Min(0) Integer children, @NotNull @Min(0) Integer salary)]. Ein Parameter [@Valid @RequestBody TaxRequest request] wird dann vor dem Aufruf der Methode validiert, und eine ungültige Anfrage wird mit einer 400-Antwort „Problem Details“ abgelehnt, wie wir sie selbst erstellt haben.

    13.7.4. Hosting

    Unsere Services werden mit [mvn spring-boot:run] ausgeführt, was für die Entwicklung geeignet ist. In der Produktion:

    • Die Anwendung wird zunächst mit [mvn package] paketiert: Das Spring-Boot-Plugin erzeugt eine einzige „ausführbare“ [.jar]-Datei, die die Anwendung, ihre Abhängigkeiten und den Tomcat-Server enthält. Sie kopieren sie einfach auf den Server und führen sie mit [java -jar ws-tax-9.0.jar] aus; die Konfiguration lässt sich über Kommandozeilenargumente ([--server.port=80]), Umgebungsvariablen oder eine Datei [application.properties] ändern, die neben der Datei [.jar] liegt;
    • Tomcat kann direkt dem Internet ausgesetzt werden, wird aber häufig hinter einem Reverse-Proxy (nginx oder Apache unter Linux, IIS unter Windows) platziert, der HTTPS-Anfragen entgegennimmt, Zertifikate verwaltet und die Last auf mehrere Instanzen der Anwendung verteilt;
    • Die Anwendung kann auch als Container-Image (Docker) bereitgestellt werden, das das Spring-Boot-Plugin ohne eine Datei [Dockerfile] erzeugen kann: [mvn spring-boot:build-image]. Das Image läuft dann auf jeder Container-Plattform, sei es auf Ihrem eigenen Server oder bei einem Hosting-Anbieter;
    • HTTPS ist unverzichtbar: Die Spring-Boot-Eigenschaften [server.ssl.*] konfigurieren das Zertifikat des Tomcat-Servers, wenn der Server direkt exponiert ist.

    13.8. Fazit

    Dieses Kapitel hat die REST/JSON-Webservices, die Nachfolger der SOAP-Webservices, vorgestellt, die mit Spring Boot und Spring MVC geschrieben werden. Wir haben Folgendes gesehen:

    • dass ein Webservice URLs und HTTP-Methoden mit den Annotationen [@RestController], [@GetMapping] und [@PostMapping] auf Java-Methoden abbildet und dass die Parameter dieser Methoden aus der Route ([@PathVariable]), dem Query-String ([@RequestParam]), dem Body (JSON, [@RequestBody]) oder dem Spring-Container (Konstruktorinjektion) stammen;
    • dass die Ergebnisse von Jackson als JSON gesendet werden und Fehler über einen Statuscode und ein „Problem Details“-Dokument gemeldet werden ([ProblemDetail], [ResponseEntity], [@ExceptionHandler]);
    • dass ein Java-Client [java.net.http.HttpClient] und Jackson verwendet und dass ein in einer beliebigen anderen Sprache geschriebener Client dasselbe tun kann;
    • dass die Schichtenarchitektur ihre Versprechen gehalten hat: Version 9 der Steuerberechnung verwendet die serverseitigen Schichten [dao] and [business] aus Version 5 ebenso wie deren clientseitige Schicht [ui] unverändert wieder; Es genügte, den Webservice (etwa 100 Zeilen) und eine neue Implementierung der Schnittstelle [ITaxBusiness] (etwa 60 Zeilen) zu schreiben.

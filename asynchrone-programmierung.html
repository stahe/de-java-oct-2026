    9. Asynchrone Programmierung

    Das vorherige Kapitel hat Threads eingeführt: Wir können mehrere Codestücke „gleichzeitig“ ausführen, sie synchronisieren und Aufgaben über einen Executor ([ExecutorService]) einem Thread-Pool zuweisen. Dieses Kapitel behandelt ein verwandtes, aber eigenständiges Problem: wie man ein Programm schreibt, das viel wartet (auf die Festplatte, das Netzwerk oder eine Datenbank), ohne während dieser Wartezeiten Threads zu binden.

    Java hat dafür keine Sprachschlüsselwörter (andere Sprachen wie C# oder JavaScript haben die Schlüsselwörter [async] und [await]). Es bietet zwei Lösungen an, die sich ergänzen und beide in diesem Kapitel vorgestellt werden:

    • die Klasse [CompletableFuture<T>] (Java 8, seither erweitert) stellt eine laufende Operation dar, deren nachfolgende Schritte mithilfe von Callback-Methoden zusammengesetzt werden: „Wenn das Ergebnis bereit ist, tue dies, dann das“ ([thenApply], [thenCompose], [thenCombine], [allOf] …). Kein Thread wartet: Der Abschluss der Operation löst den nächsten Schritt aus;
    • virtuelle Threads ( Java 21) erlauben es dagegen, blockierenden, sequenziellen Code zu schreiben, der sich von oben nach unten liest: Wartet ein virtueller Thread auf Ein-/Ausgabe, löst die JVM ihn von dem Systemthread, der ihn ausgeführt hat (seinem „Trägerthread“), und gibt diesen Thread für einen anderen virtuellen Thread frei. So sind Hunderttausende virtueller Threads auf nur wenigen Systemthreads möglich. Das ist die moderne Lösung von Java für das Problem, das andere Sprachen mit [async] / [await] lösen.

    Diese Werkzeuge sind heute allgegenwärtig: Die folgenden Kapitel setzen sie ein, um auf Datenbanken zuzugreifen, TCP-Server zu schreiben, die jeden Client über einen virtuellen Thread bedienen, Web-Clients mit [java.net.http.HttpClient] und Webdienste mit Spring Boot.

    Alle Beispiele dieses Kapitels sind kompakte Quelldateien ([Async01.java], [Async02.java] …), die mit [java AsyncNN.java] im Ordner [09-async] ausgeführt werden. Viele davon messen Ausführungszeiten mit [System.nanoTime()]: Die angezeigten Millisekunden variieren von Lauf zu Lauf und von Rechner zu Rechner (die Beispiele wurden auf einem Rechner mit zwei Prozessoren ausgeführt). Es kommt auf die Größenordnungen an: 1 Sekunde oder 10 Sekunden, 300 ms oder 0 ms.

    9.1. Warum Asynchronität

    9.1.1. Operationen, die warten

    Ein Programm verrichtet zwei Arten von Arbeit:

    • Rechenaufgaben, die den Prozessor beanspruchen: eine Liste sortieren, eine Steuer berechnen, einen Text analysieren;
    • Ein-/Ausgabe (E/A), die im Wesentlichen im Warten auf ein Peripheriegerät besteht: eine Datei von der Festplatte lesen, eine Anfrage an einen Webserver senden und auf seine Antwort warten, eine SQL-Abfrage auf einem Datenbankserver ausführen.

    Die Größenordnungen sind sehr unterschiedlich. Ein Prozessor führt einige Milliarden Anweisungen pro Sekunde aus. Ein Lesevorgang auf einer Festplatte (SSD) dauert etwa eine Zehntelmillisekunde; ein Hin- und Rückweg in einem lokalen Netzwerk dauert den Bruchteil einer Millisekunde; ein Hin- und Rückweg zu einem Server am anderen Ende des Landes dauert einige zehn Millisekunden; und eine etwas komplexere SQL-Abfrage kann mitunter mehrere Sekunden dauern. Während dieser Wartezeiten hätte der Prozessor Millionen von Anweisungen ausführen können.

    Wenn ein Programm mit einer blockierenden Methode eine Zeile über eine Netzwerkverbindung liest, ist der Thread, der diesen Lesevorgang ausführt, blockiert: Er tut nichts, existiert aber weiterhin. Ein „klassischer“ Java-Thread – heute als „Plattform-Thread“ bezeichnet – ist ein Thread des Betriebssystems: Er belegt Speicher (seinen Stack, in der Größenordnung eines Megabytes), er ist dem System bekannt, und vor allem steht er nicht mehr für andere Aufgaben zur Verfügung. In einem kleinen Konsolenprogramm, das jeweils nur eine Sache tut, ist das kein Problem. In zwei Situationen wird es deutlich problematischer:

    • in einem Server: Jeder Client, der von einem blockierten Thread bedient wird, bindet diesen Thread. Hat der Thread-Pool des Servers N Threads und führen alle N Threads eine blockierende Operation aus, bleibt für einen neuen Client kein Thread mehr verfügbar. Ein moderner Server bearbeitet Tausende gleichzeitiger Anfragen: Das ist möglich, weil seine Warteoperationen keine Systemthreads binden;
    • in einer grafischen Benutzeroberfläche: Ein einziger Thread – der UI-Thread (der „Event Dispatch Thread“ von Swing, der „JavaFX Application Thread“) – bearbeitet Klicks und zeichnet Fenster neu. Wird er durch einen Download blockiert, friert das Fenster ein.

    Asynchronität bedeutet, die E/A-Operation zu starten, den Systemthread freizugeben, solange sie läuft (die Hardware und das Betriebssystem brauchen ihn nicht, um Daten zu übertragen), und die Arbeit nach Abschluss der Operation fortzusetzen, gegebenenfalls auf einem anderen Systemthread:

    • In [1]startet der Plattform-Thread T1 die E/A und bleibt blockiert, bis sie beendet ist;
    • in [2]startet der virtuelle Thread V1 die E/A; die JVM löst ihn von seinem Trägerthread P1, der dann sofort andere virtuelle Threads ausführen kann. Wenn die E/A abgeschlossen ist, verbindet die JVM V1 wieder mit einem freien Trägerthread, P2 (der auch P1 sein könnte), und V1 setzt seine Ausführung unmittelbar nach der blockierenden Anweisung fort, als sei nichts geschehen.

    Das Programm [Async01.java] misst den Unterschied bei 100 Operationen, die jeweils eine Sekunde warten (das Warten simuliert E/A). Es verwendet Anweisungen, die wir später in diesem Kapitel erklären ([Executors.newVirtualThreadPerTaskExecutor], [CompletableFuture]): Hier interessieren uns vor allem die Ergebnisse.

    // warum Asynchronität: 100 Operationen, die jeweils eine Sekunde warten
// (ein Warten simuliert eine E/A: Festplattenlesen, Netzwerkanfrage, SQL-Abfrage…)
import java.lang.management.ManagementFactory;

final int nbOperations = 100;
long start;

void main() throws InterruptedException {
    IO.println(nbOperations + " operations of one second, "
            + Runtime.getRuntime().availableProcessors() + " processors");

    // 1 - ein Plattform-Thread pro Operation, jeder Thread ist während des Wartens blockiert
    start = System.nanoTime();
    List<Thread> threads = new ArrayList<>();
    for (int i = 0; i < nbOperations; i++) {
        threads.add(Thread.ofPlatform().start(() -> waitFor(1000)));
    }
    display("1 - one platform thread per operation", jvmThreads());
    for (Thread thread : threads) {
        thread.join();
    }
    display("    end", -1);

    // 2 - die Operationen werden einem Pool aus 10 Threads übergeben, blockieren ihn aber
    start = System.nanoTime();
    try (ExecutorService pool = Executors.newFixedThreadPool(10)) {
        for (int i = 0; i < nbOperations; i++) {
            pool.submit(() -> waitFor(1000));
        }
        display("2 - pool of 10 threads, blocking waits", jvmThreads());
    } // close() wartet auf das Ende aller Operationen
    display("    end", -1);

    // 3 - ein virtueller Thread pro Operation: er gibt während des Wartens seinen Carrier-Thread frei
    start = System.nanoTime();
    try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
        for (int i = 0; i < nbOperations; i++) {
            executor.submit(() -> waitFor(1000));
        }
        display("3 - one virtual thread per operation", jvmThreads());
    }
    display("    end", -1);

    // 4 - asynchrone Wartezeiten: kein Thread wartet, ein Timer schließt jede Operation ab
    start = System.nanoTime();
    var operations = new CompletableFuture<?>[nbOperations];
    for (int i = 0; i < nbOperations; i++) {
        operations[i] = new CompletableFuture<Void>().completeOnTimeout(null, 1000, TimeUnit.MILLISECONDS);
    }
    display("4 - asynchronous waits (CompletableFuture)", jvmThreads());
    CompletableFuture.allOf(operations).join();
    display("    end", -1);
}

// ein blockierendes Warten von [ms] Millisekunden
void waitFor(long ms) {
    try {
        Thread.sleep(ms);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
}

// Anzahl der Plattform-Threads der JVM, eine halbe Sekunde nach dem Start der Operationen
int jvmThreads() {
    long elapsed = (System.nanoTime() - start) / 1_000_000;
    if (elapsed < 500) {
        waitFor(500 - elapsed);
    }
    return ManagementFactory.getThreadMXBean().getThreadCount();
}

// Anzeige der verstrichenen Zeit und, falls angegeben (>= 0), der Anzahl der Threads
void display(String message, int nbThreads) {
    String threadsInfo = nbThreads < 0 ? "" : String.format(", %3d threads in the JVM", nbThreads);
    long elapsed = (System.nanoTime() - start) / 1_000_000;
    IO.println(String.format("%-44s : %5d ms%s", message, elapsed, threadsInfo));
}

    Erläuterungen:

    • Zeilen 12–22: die einfachste Lösung – ein Plattform-Thread pro Operation. [Thread.ofPlatform().start(task)] (Java 21) erzeugt und startet einen Thread, genau wie [new Thread(task).start()]. Jeder Thread führt [Thread.sleep(1000)] aus: Er ist eine Sekunde lang blockiert. Die 100 Wartevorgänge laufen gleichzeitig ab, und der gesamte Vorgang dauert genau eine Sekunde (Zeile 4 der Ergebnisse), jedoch um den Preis von 100 zusätzlichen Systemthreads: Die JVM hat 106 davon (Zeile 3). Bei 10.000 Operationen wären 10.000 Systemthreads erforderlich;
    • Zeilen 24–32: Die Operationen werden einem Pool aus 10 Threads zugewiesen ([Executors.newFixedThreadPool(10)]), eine für Berechnungen vernünftige Größe. Hier rechnen diese Threads aber nicht – sie sind untätig. Die Operationen warten in Gruppen von 10 auf einen freien Thread, und der gesamte Vorgang dauert … zehn Sekunden (Zeile 6). Das nennt man „Thread-Pool-Starvation“, den häufigsten Fehler in Servern, die Thread-Pools mit blockierender E/A mischen. Die Methode [close()] eines Executors (Java 19), die beim Verlassen von [try] aufgerufen wird, lehnt neue Aufgaben ab und wartet, bis die übergebenen beendet sind;
    • Zeilen 34–42: Ein virtueller Thread pro Operation. [Executors.newVirtualThreadPerTaskExecutor()] (Java 21) gibt einen Executor zurück, der für jede übergebene Aufgabe einen neuen virtuellen Thread erzeugt. Der Code der Aufgabe ist derselbe wie in Schritt 1: ein blockierendes [Thread.sleep(1000)]. Ein blockierter virtueller Thread bindet jedoch keinen Systemthread: Die JVM löst ihn von seinem Trägerthread. Die 100 Wartevorgänge dauern insgesamt eine Sekunde (Zeile 8), und die JVM zählt nur 10 Systemthreads (Zeile 7): ihre Dienst-Threads und die beiden Trägerthreads – einer pro Prozessor –, die die 100 virtuellen Threads ausgeführt haben. Die virtuellen Threads sind in dieser Zählung nicht enthalten: Sie sind Objekte der JVM, keine Systemthreads;
    • Zeilen 44–52: dasselbe Warten ohne wartende Threads. [new CompletableFuture<Void>()] erzeugt eine „ausstehende“ Operation, und [completeOnTimeout(value, timeout, unit)] (Java 9) fordert an, dass sie nach Ablauf der Zeitspanne mit dem angegebenen Wert abgeschlossen wird. Ein einziger Timer der JVM verwaltet die 100 Zeitüberschreitungen. [CompletableFuture.allOf(...)] gibt eine Operation zurück, die abgeschlossen ist, wenn alle anderen beendet sind, und [join()] wartet auf ihr Ende. Der gesamte Vorgang dauert eine Sekunde (Zeile 10), mit nur einem zusätzlichen Thread gegenüber Schritt 3 – dem Timer-Thread (Zeile 9);
    • Zeilen 55–62: [Thread.sleep] kann die geprüfte Ausnahme [InterruptedException] auslösen, wenn der Thread während des Schlafens unterbrochen wird (darauf gehen wir im Abschnitt über den Abbruch noch ein); die Methode [waitFor] fängt sie ab, damit die Lambdas in den Zeilen 16, 28 und 38 sie nicht behandeln müssen;
    • Zeilen 64–71: [ManagementFactory.getThreadMXBean().getThreadCount()] gibt die Anzahl der lebenden Plattform-Threads der JVM zurück. Die Klasse [ManagementFactory] gehört zum Modul [java.management]: Eine kompakte Quelldatei importiert automatisch nur das Modul [java.base], daher der Import in Zeile 3.

    Merken wir uns die Lehre: Um zu warten, darf man keine Systemthreads blockieren. Asynchronität macht E/A nicht schneller; sie ermöglicht es, eine große Anzahl von E/A-Operationen gleichzeitig mit wenigen Systemthreads zu bewältigen und dabei die von der Anwendung benötigten Threads verfügbar zu halten. Java bietet hierfür zwei Ansätze: [CompletableFuture] zu erzeugen (Schritt 4) oder gewöhnlichen blockierenden Code zu schreiben, der von virtuellen Threads ausgeführt wird (Schritt 3).

    9.1.2. Mehrere aufeinanderfolgende Modelle

    Java hat mehrere Möglichkeiten angeboten, Code zu schreiben, der wartet, ohne zu blockieren. Die älteren finden sich noch in bestehendem Code, daher ist es nützlich, sie zu erkennen.

    Muster
    Einführung
    Prinzip
    [Future] und Runtimes
    Java 5 (2004)
    [ExecutorService.submit] weist einem Thread-Pool eine Aufgabe zu und gibt ein [Future<T>] zurück, das das kommende Ergebnis darstellt. Dieses Ergebnis lässt sich aber nur durch blockierendes Warten mit [get()] erhalten.
    Callback-Methoden von NIO.2
    Java 7 (2011)
    Asynchrone Kanäle ([AsynchronousSocketChannel], [AsynchronousFileChannel]) starten eine Operation und erhalten ein Callback-Objekt ([CompletionHandler]), dessen Methode [completed] oder [failed] nach Abschluss der Operation von einem Thread aus einem Pool aufgerufen wird.
    [CompletableFuture]
    Java 8 (2014)
    ein [Future] , das Sie selbst abschließen können und dessen Ablauf aus Callback-Methoden zusammengesetzt wird ([thenApply], [thenCompose], [exceptionally] …); reaktive Streams [java.util.concurrent.Flow] (Java 9) sind eine Erweiterung davon für Wertfolgen. Reaktive Bibliotheken (Project Reactor, von Spring WebFlux verwendet, RxJava) beruhen auf denselben Konzepten.
    virtuelle Threads
    Java 21 (2023)
    gewöhnlicher blockierender Code, der von virtuellen Threads ausgeführt wird: Die JVM gibt den Systemthread während des Wartens frei. Das ist heute das empfohlene Modell für neue Anwendungen.
    strukturierte Nebenläufigkeit
    Vorschau von Java 21 bis Java 25
    [StructuredTaskScope] organisiert eine Gruppe von Teilaufgaben, die von virtuellen Threads ausgeführt werden, als einen einzigen Codeblock, mit gemeinsamer Fehlerbehandlung und gemeinsamem Abbruch (siehe das Ende des Kapitels).

    Callback-Methoden haben einen Nachteil: Der Code wird zerstückelt. Was sich natürlich als „verbinden, dann lesen, dann anzeigen“ liest, wird zu einer Methode, die die Verbindung startet, einer Callback-Methode, die den Lesevorgang startet, und einer weiteren Callback-Methode, die das Ergebnis anzeigt; Variablen müssen zwischen diesen Methoden geteilt werden, Ausnahmen werden an verschiedenen Stellen abgefangen, und eine einfache Schleife („lesen, solange Daten vorhanden sind“) wird zu einer Callback-Methode, die sich rekursiv selbst aufruft. [CompletableFuture] macht diese Zerstückelung lesbarer, indem es die Schritte verkettet; virtuelle Threads lassen sie verschwinden: Asynchroner Code nimmt die Form synchronen Codes an, weil er tatsächlich synchroner Code ist.

    Das Programm [Async02.java] implementiert denselben TCP-Client mit zwei extremen Ansätzen: zunächst mit den Callback-Methoden von NIO.2, dann mit blockierendem Code, der von einem virtuellen Thread ausgeführt wird. Es enthält außerdem einen kleinen Server, der von einem Thread betrieben wird und zwei Clients antwortet (die Netzwerkprogrammierung wird in Kapitel 12 ausführlich behandelt; vorerst genügt es zu wissen, dass ein Client sich mit dem Server verbindet und die Nachricht liest, die der Server ihm sendet).

    // derselbe TCP-Client, geschrieben mit Callback-Methoden (NIO.2, Java 7) und dann mit einem virtuellen Thread (Java 21)
final int port = 27500;
final InetAddress local = InetAddress.getLoopbackAddress();
final ByteBuffer buffer = ByteBuffer.allocate(1024);
final CountDownLatch end = new CountDownLatch(1);

void main() throws IOException, InterruptedException {
    // ein minimaler Server, von einem Thread ausgeführt: er bedient zwei Clients und endet dann
    var listener = new ServerSocket(port, 10, local);
    Thread server = Thread.ofPlatform().name("server").start(() -> {
        try (listener) {
            for (int i = 1; i <= 2; i++) {
                try (Socket service = listener.accept()) {
                    // der Server lässt sich mit der Antwort Zeit
                    Thread.sleep(500);
                    byte[] message = ("Hello client no. " + i).getBytes(StandardCharsets.UTF_8);
                    service.getOutputStream().write(message);
                }
            }
        } catch (IOException | InterruptedException e) {
            display("server: " + e);
        }
    });
    display("start of the program");

    // 1 - der Stil "Callback-Methoden": AsynchronousSocketChannel und CompletionHandler
    var client = AsynchronousSocketChannel.open();
    // wir starten die Verbindung und geben das Objekt an, das nach ihrem Abschluss aufgerufen wird
    client.connect(new InetSocketAddress(local, port), client, new Connected());
    display("callbacks: connection started, the program continues");
    // der Haupt-Thread hat nichts mehr zu tun: er wartet auf das Signal der letzten Callback-Methode
    end.await();

    // 2 - der blockierende Stil, von einem virtuellen Thread ausgeführt: der Code liest sich von oben nach unten
    Thread virtual = Thread.ofVirtual().start(() -> {
        try (var client2 = new Socket(local, port)) {
            display("virtual thread: connected, read started");
            byte[] bytes = new byte[1024];
            int nbBytes = client2.getInputStream().read(bytes);
            String message = new String(bytes, 0, nbBytes, StandardCharsets.UTF_8);
            display("virtual thread: received [" + message + "]");
        } catch (IOException e) {
            display("virtual thread: " + e);
        }
    });
    virtual.join();
    server.join();
}

// Callback-Methode Nr. 1: die Verbindung steht (oder ist fehlgeschlagen)
class Connected implements CompletionHandler<Void, AsynchronousSocketChannel> {
    @Override
    public void completed(Void nothing, AsynchronousSocketChannel channel) {
        display("callbacks: connected, read started");
        // wir starten das Lesen der Serverantwort mit einem anderen Callback-Objekt
        channel.read(buffer, channel, new Received());
    }

    @Override
    public void failed(Throwable e, AsynchronousSocketChannel channel) {
        display("callbacks: connection failed: " + e);
        end.countDown();
    }
}

// Callback-Methode Nr. 2: Daten sind eingetroffen
class Received implements CompletionHandler<Integer, AsynchronousSocketChannel> {
    @Override
    public void completed(Integer nbBytes, AsynchronousSocketChannel channel) {
        display("callbacks: received [" + new String(buffer.array(), 0, nbBytes, StandardCharsets.UTF_8) + "]");
        try {
            channel.close();
        } catch (IOException e) {
            display("callbacks: " + e);
        }
        // wir benachrichtigen den Haupt-Thread
        end.countDown();
    }

    @Override
    public void failed(Throwable e, AsynchronousSocketChannel channel) {
        display("callbacks: read failed: " + e);
        end.countDown();
    }
}

// Ausgabe mit dem ausführenden Thread als Präfix
// (Name eines Plattform-Threads, Beschreibung eines virtuellen Threads)
void display(String message) {
    Thread thread = Thread.currentThread();
    IO.println("[" + (thread.isVirtual() ? thread.toString() : thread.getName()) + "] " + message);
}

    9.2. Kommende Aufgaben: Future und CompletableFuture

    Ein [Future<T>] (Schnittstelle des Pakets [java.util.concurrent], Java 5) ist ein Objekt, das das Ergebnis – vom Typ [T] – einer laufenden oder beendeten Operation darstellt. Wir sind ihm im vorherigen Kapitel begegnet: Es ist das, was die Methode [submit] eines Executors zurückgibt. Sie können es abfragen (ist es beendet? war es erfolgreich?), abbrechen ([cancel]) und auf sein Ergebnis warten ([get]), aber nicht mehr: Das Ergebnis lässt sich nur verwenden, indem man einen Thread blockiert, bis es verfügbar ist.

    Die Klasse [CompletableFuture<T>] (Java 8) implementiert [Future<T>] und fügt zwei wesentliche Fähigkeiten hinzu:

    • Sie können es selbst beenden, mit einem Ergebnis ([complete]) oder mit einer Ausnahme ([completeExceptionally]);
    • Sie können daran eine Folgeoperation anhängen – eine Funktion, die ausgeführt wird, sobald das Ergebnis verfügbar ist ([thenApply], [thenAccept], [thenCompose] …) und die ein neues [CompletableFuture] erzeugt. So entstehen Operationsketten, ohne dass ein Thread warten muss. Diese Methoden werden von der Schnittstelle [CompletionStage<T>] deklariert, die [CompletableFuture] ebenfalls implementiert.

    Ein [CompletableFuture] ist kein Thread. Er kann einen Vorgang darstellen, der von einem Thread eines Executors ausgeführt wird (wie bei den mit [supplyAsync] erzeugten), aber viele werden von keinem Thread ausgeführt: Der in Schritt 4 von [Async01.java] wird einfach nach einer Sekunde von einem Timer „abgeschlossen“, und der von [HttpClient.sendAsync] zurückgegebene wird abgeschlossen, wenn die Antwort des Servers eintrifft. Er ist ein Versprechen auf ein Ergebnis.

    9.3. Asynchrone Methoden

    9.3.1. Erster Ansatz: ein CompletableFuture zurückgeben

    In Java ist eine asynchrone Methode einfach eine Methode, die eine Operation startet und sofort, ohne zu warten, ein [CompletableFuture] zurückgibt, das sie darstellt:

    • [CompletableFuture<Void>] , wenn die Operation kein Ergebnis liefert;
    • [CompletableFuture<T>] , wenn sie ein Ergebnis vom Typ [T] liefert.

    9.3.3. Was die JVM tut

    Wie kann ein virtueller Thread mitten in einer Schleife unterbrochen werden, seinen Trägerthread freigeben und später an derselben Stelle mit denselben Werten der lokalen Variablen fortgesetzt werden, möglicherweise auf einem anderen Trägerthread? Ein virtueller Thread ist ein Java-Objekt ([java.lang.VirtualThread], eine von [Thread] abgeleitete Klasse), das einen eigenen Aufrufstack hat. Zur Ausführung „montiert“ die JVM ihn auf einen Trägerthread – einen Plattform-Thread eines hierfür reservierten [ForkJoinPool] , der standardmäßig so viele Threads hat, wie Prozessoren vorhanden sind. Ruft der virtuelle Thread eine blockierende Operation auf ([Thread.sleep], Lesen von einem Socket; [BlockingQueue.take], Warten auf eine Sperre …), blockieren die Klassen der JVM – hierfür in Java 21 neu geschrieben – den tragenden Thread nicht:

    • sie registrieren die Operation beim System (ein Timer für eine Verzögerung, der E/A-Benachrichtigungsmechanismus des Systems – [epoll] unter Linux – für einen Socket);
    • sie „demontieren“ den virtuellen Thread: Die Frames seines Aufrufstacks werden als Objekt namens Continuation auf den Heap kopiert, und der Trägerthread wird an den [ForkJoinPool] zurückgegeben, der ihm einen anderen ausführungsbereiten virtuellen Thread zuweist;
    • Wenn die Operation abgeschlossen ist, wird der virtuelle Thread wieder ausführungsbereit: Er wird auf den ersten verfügbaren Trägerthread neu montiert, seine Stack-Frames werden wieder kopiert, und die Ausführung wird unmittelbar nach dem blockierenden Aufruf fortgesetzt.

    Das ist das Prinzip hinter Callback-Methoden („ruf mich zurück, wenn die Operation abgeschlossen ist“), aber es ist die JVM, die die Ausführung zerlegt, die Variablen sichert und den Kontext auf der Ebene des Aufrufstacks wiederherstellt, ohne dass der Quellcode eine Spur davon zeigt. Andere Sprachen übertragen diese Aufgabe dem Compiler, der jede [async]-Methode in eine „Zustandsmaschine“ umwandelt; Java überträgt sie der JVM, die dadurch den gesamten bestehenden Code auf dieselbe Weise behandeln kann.

    Es sind zwei Einschränkungen zu beachten:

    • Bestimmte Operationen können den virtuellen Thread nicht ablösen; er bleibt daher an seinen Host-Thread „gepinnt“, der während des Wartens blockiert ist. Dies geschieht während der Ausführung einer nativen Methode und bei den meisten Lese- und Schreibzugriffen auf Dateien (das System bietet für Dateien keine Benachrichtigung, die von der JVM genutzt werden kann); in diesem Fall [ForkJoinPool] kompensiert dies, indem er vorübergehend einen zusätzlichen Carrier-Thread erzeugt. Bis Java 23 galt dies auch für einen virtuellen Thread, der innerhalb eines [synchronized]-Blocks wartet; seit Java 24 ist das nicht mehr der Fall;
    • Ein virtueller Thread beschleunigt keine Berechnung: Ein virtueller Thread, der eine Berechnung durchführt, belegt seinen Host-Thread für die gesamte Dauer der Berechnung. Virtuelle Threads sind für Programme gedacht, die viel warten, nicht für solche, die viel rechnen (für Letztere stehen Thread-Pools und parallele Streams aus dem vorigen Kapitel zur Verfügung).

    • Der gemeinsame Pool eignet sich für kurze Fortsetzungen und kurze Berechnungen; blockierende Operationen sollten dort nicht ausgeführt werden, da sonst die in [Async01.java] beschriebene Starvation droht (er hat auf unserem Rechner nur einen Thread);

    9.6. Abbruch und Fristen

    9.6.1. Future.cancel und Beenden von Threads

    Eine lang laufende Operation muss abgebrochen werden können: Der Benutzer hat auf [Cancel] geklickt, ein Client hat die Verbindung zum Server getrennt, die Anwendung wurde beendet oder eine Zeitüberschreitung ist eingetreten. Java verwendet dafür einen kooperativen Mechanismus – die Unterbrechung von Threads:

    • Die Methode [interrupt()] eines Threads setzt dessen Unterbrechungsflag; sie beendet den Thread nicht (die Methode [Thread.stop], die einen Stopp erzwang, ist seit Java 20 veraltet: Sie löst eine [UnsupportedOperationException] aus);
    • Wenn der Thread in einem unterbrechbaren Warten blockiert ist ([Thread.sleep], [Object.wait], [Thread.join], [BlockingQueue.take], [Future.get] …), wird das Warten sofort unterbrochen und löst eine [InterruptedException] aus, wobei das Flag zurückgesetzt wird;
    • Ein Thread, der Berechnungen durchführt, prüft regelmäßig sein eigenes Flag mit [Thread.currentThread().isInterrupted()] und beendet sich ordnungsgemäß, wenn es gesetzt ist;
    • Die Methode [cancel(true)] eines von einem Executor gelieferten [Future] versetzt die Aufgabe in den Zustand [CANCELLED] und unterbricht den Thread, der sie ausführt ([cancel(false)] verhindert lediglich, dass die Aufgabe startet, falls sie noch nicht begonnen hat). Nach dem Abbruch löst [get()] eine [CancellationException] aus.

    Der Mechanismus ist kooperativ: Niemand stoppt eine Operation zwangsweise; die Operation hält sich selbst an einer Stelle an, an der sie dies sauber tun kann. Deshalb darf eine Methode, die eine [InterruptedException] abfängt, sie nicht ignorieren: Sie muss sie entweder weitergeben, sich selbst beenden oder zumindest das Flag mit [Thread.currentThread().interrupt()] wieder setzen, damit der aufrufende Code weiß, dass eine Unterbrechung angefordert wurde (das tut unsere Methode [sleep]).

// eine auf [timeout] Millisekunden begrenzte Verarbeitung, die auch vom Aufrufer gestoppt werden kann
CompletableFuture<Void> processWithTimeout(String name, int duration, int timeout, CompletableFuture<Void> stop) {
    CompletableFuture<String> answer = query(name, duration).orTimeout(timeout, TimeUnit.MILLISECONDS);
    // der allgemeine Stopp bricht das Warten auf die Antwort ab
    stop.thenRun(() -> answer.cancel(false));
    // wir untersuchen, wie das Warten geendet hat
    return answer.handle((text, e) -> switch (e) {
        case null -> text;
        case TimeoutException _ -> name + " : timeout of " + timeout + " ms exceeded";
        case CancellationException _ -> name + " : stopped at the caller's request";
        default -> name + " : " + e;
    }).thenAccept(message -> display("4 - " + message));
}

// liest eine ganze (kleine) Datei mit einem AsynchronousFileChannel
CompletableFuture<String> readAsynchronously(Path file) {
    CompletableFuture<String> result = new CompletableFuture<>();
    try {
        AsynchronousFileChannel channel = AsynchronousFileChannel.open(file, StandardOpenOption.READ);
        ByteBuffer buffer = ByteBuffer.allocate((int) channel.size());
        // das Lesen wird gestartet; das Callback-Objekt schließt das CompletableFuture ab
        channel.read(buffer, 0, buffer, new CompletionHandler<Integer, ByteBuffer>() {
            @Override
            public void completed(Integer nbBytes, ByteBuffer read) {
                result.complete(new String(read.array(), 0, nbBytes, StandardCharsets.UTF_8));
            }

            @Override
            public void failed(Throwable e, ByteBuffer read) {
                result.completeExceptionally(e);
            }
        });
        // der Channel wird geschlossen, wenn das Lesen beendet ist, unabhängig vom Ausgang
        result.whenComplete((text, e) -> close(channel));
    } catch (IOException e) {
        result.completeExceptionally(e);
    }
    return result;
}

void processFiles() throws IOException {
    // 2 - die ganze Datei in einer einzigen Operation lesen
    List<String> lines = Files.readAllLines(data);
    IO.println("2 - Files.readAllLines: " + lines.size() + " lines");

    // 3 - zeilenweises Lesen mit einem BufferedReader
    List<TaxBracket> brackets = new ArrayList<>();
    try (BufferedReader reader = Files.newBufferedReader(data)) {
        String line;
        // readLine gibt am Dateiende null zurück
        while ((line = reader.readLine()) != null) {
            brackets.add(TaxBracket.parse(line));
        }
    }
    IO.println("3 - BufferedReader.readLine: " + brackets.size() + " brackets, 2nd: " + brackets.get(1));

    // 4 - Files.lines liefert einen Stream von Zeilen, bei Bedarf gelesen
    try (Stream<String> stream = Files.lines(data)) {
        IO.println("4 - Files.lines: " + stream.count() + " lines");
    }

    // 5 - Schreiben mit einem BufferedWriter
    try (BufferedWriter writer = Files.newBufferedWriter(report)) {
        writer.write("Brackets of the tax scale (exercise: 2004 tax scale on 2003 income)");
        writer.newLine();
        for (int i = 0; i < brackets.size(); i++) {
            TaxBracket bracket = brackets.get(i);
            String limit = bracket.limit().signum() == 0 ? "beyond"
                    : String.format("up to %,d €", bracket.limit().intValue());
            writer.write(String.format("bracket %d : %-18s rate %.1f %%",
                    i + 1, limit, bracket.coeffR().multiply(BigDecimal.valueOf(100))));
            writer.newLine();
        }
    }

import com.sun.net.httpserver.HttpServer;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;

final int port = 27510;
final List<String> cities = List.of("Angers", "Brest", "Colmar", "Dijon", "Évry", "Foix");
long start;

void main() throws IOException, InterruptedException, ExecutionException {
    // ein HTTP-Server, der eine Sekunde braucht, um die "Temperatur" einer Stadt zu liefern
    HttpServer server = HttpServer.create(new InetSocketAddress(InetAddress.getLoopbackAddress(), port), 0);
    server.createContext("/temperature", exchange -> {
        // die Anfrage hat die Form /temperature?city=xxx
        String parameter = exchange.getRequestURI().getRawQuery().substring("city=".length());
        String city = URLDecoder.decode(parameter, StandardCharsets.UTF_8);
        sleep(1000);
        byte[] response = (city + " : " + (10 + city.length()) + " °C").getBytes(StandardCharsets.UTF_8);
        exchange.sendResponseHeaders(200, response.length);
        try (OutputStream stream = exchange.getResponseBody()) {
            stream.write(response);
        }
    });
    // jede empfangene Anfrage wird von einem virtuellen Thread bearbeitet
    server.setExecutor(Executors.newVirtualThreadPerTaskExecutor());
    server.start();

    try (HttpClient client = HttpClient.newBuilder().version(HttpClient.Version.HTTP_1_1).build()) {
        // eine erste Anfrage, damit die JVM die Client-Klassen vor den Messungen lädt
        client.send(request("Paris"), HttpResponse.BodyHandlers.discarding());

        // 1 - sendAsync liefert sofort ein CompletableFuture<HttpResponse<String>>
        start = System.nanoTime();
        List<CompletableFuture<String>> responses = cities.stream()
                .map(city -> client.sendAsync(request(city), HttpResponse.BodyHandlers.ofString())
                        .thenApply(HttpResponse::body))
                .toList();
        CompletableFuture.allOf(responses.toArray(CompletableFuture[]::new)).join();
        display("1 - sendAsync: " + responses.stream().map(CompletableFuture::resultNow).toList());

        // 2 - send ist blockierend: wir rufen es aus virtuellen Threads auf
        start = System.nanoTime();
        try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
            List<Future<String>> responses2 = new ArrayList<>();
            for (String city : cities) {
                responses2.add(executor.submit(
                        () -> client.send(request(city), HttpResponse.BodyHandlers.ofString()).body()));
            }
            List<String> texts = new ArrayList<>();
            for (Future<String> response : responses2) {
                texts.add(response.get());
            }
            display("2 - send on virtual threads: " + texts);
        }
    } finally {
        server.stop(0);
    }
}

    9.9. Asynchrone Wertströme

    Eine asynchrone Operation liefert nach einer gewissen Zeit ein Ergebnis. Ein Stream ([Stream]) oder ein Iterator liefert eine Folge von Werten, die bei Bedarf erzeugt werden. Manchmal müssen beide kombiniert werden: eine Folge von Werten, bei der vor der Erzeugung jedes Werts gewartet werden muss. Das ist der Fall bei den Zeilen einer großen Datei, den Zeilen im Ergebnis einer SQL-Abfrage, den Nachrichten, die über eine Netzwerkverbindung eintreffen, den Messwerten von Sensoren … Andere Sprachen haben dafür einen eigenen Typ; Java bietet zwei Modelle:

    • das „Pull“-Modell: Der Verbraucher fordert den nächsten Wert an und wartet, bis er verfügbar ist. Mit virtuellen Threads ist dies einfach ein [Iterator] oder ein [Stream] , bei dem die Erzeugung jedes Werts blockiert und der von einem virtuellen Thread gelesen wird;
    • das „Push“-Modell: Der Erzeuger sendet die Werte an seine Abonnenten, sobald sie erzeugt werden, und die Abonnenten steuern den Durchsatz. Dies ist das Modell der reaktiven Streams, standardisiert durch die Interfaces von [java.util.concurrent.Flow] (Java 9).

        thread.interrupt();
        thread.join();

        Thread.currentThread().interrupt();

}

    9.9.2. Das Push-Modell: Flow und SubmissionPublisher

    Das Interface [java.util.concurrent.Flow] (Java 9) fasst vier innere Interfaces zusammen, die reaktive Streams standardisieren:

    • [Flow.Publisher<T>], der Publisher, erzeugt Werte; mit seiner Methode [subscribe] wird ihm ein Subscriber hinzugefügt;
    • [Flow.Subscriber<T>], der Subscriber, erhält Werte über seine Methode [onNext], das Ende des Streams über [onComplete], einen Fehler über [onError] und zu Beginn das Objekt [Flow.Subscription], das ihn über [onSubscribe] mit dem Publisher verbindet;
    • [Flow.Subscription], das Abonnement: [request(n)] fordert zusätzliche Werte an, bis zu [n], und [cancel()] beendet das Abonnement. Der Publisher sendet nie mehr Werte, als der Subscriber angefordert hat: Das ist der „Backpressure“, der verhindert, dass ein schneller Publisher einen langsamen Subscriber überfordert;
    • [Flow.Processor<T, R>] ist zugleich Subscriber und Publisher (ein Transformationsknoten).

    Java stellt eine Implementierung des Publishers bereit, [SubmissionPublisher<T>], der die Werte über einen Executor und einen für jeden Subscriber eigenen Puffer an jeden Subscriber ausliefert. Reaktive Bibliotheken (Project Reactor, RxJava) implementieren dieselben Interfaces und ergänzen sie um Dutzende von Operatoren. // ein Abonnent, der jede Messung in [duration] ms verarbeitet und sich oberhalb von [threshold] abmeldet
class Subscriber implements Flow.Subscriber<Measurement> {
    private final String name;
    private final long duration;
    private final double threshold;
    private Flow.Subscription subscription;
    final CountDownLatch end = new CountDownLatch(1);

    Subscriber(String name, long duration, double threshold) {
        this.name = name;
        this.duration = duration;
        this.threshold = threshold;
    }

    @Override
    public void onSubscribe(Flow.Subscription subscription) {
        this.subscription = subscription;
        // der Abonnent fordert die Werte einzeln an: er steuert die Rate
        subscription.request(1);
    }

    @Override
    public void onNext(Measurement measurement) {
        display("  " + name + " : received " + measurement);
        sleep(duration);
        if (measurement.value() >= threshold) {
            display("  " + name + " : threshold reached, unsubscribing");
            subscription.cancel();
        } else {
            subscription.request(1);
        }
    }

    @Override
    public void onError(Throwable e) {
        display("  " + name + " : error " + e);
        end.countDown();
    }

    @Override
    public void onComplete() {
        display("  " + name + " : end of the stream");
        end.countDown();
    }
}

class RateService {
    // der Cache enthält die CompletableFutures selbst, abgeschlossen oder in Arbeit
    private final Map<String, CompletableFuture<BigDecimal>> cache = new ConcurrentHashMap<>();
    private final AtomicInteger nbServerAccesses = new AtomicInteger();
    private final AtomicInteger nbReadings = new AtomicInteger();

    CompletableFuture<BigDecimal> readRate(String code) {
        nbReadings.incrementAndGet();
        // ist die Währung im Cache, liefern wir das vorhandene CompletableFuture zurück: es wird kein Objekt erzeugt
        return cache.computeIfAbsent(code, this::readRateFromServer);
    }

    private CompletableFuture<BigDecimal> readRateFromServer(String code) {
        nbServerAccesses.incrementAndGet();
        // simuliert die Abfrage eines entfernten Servers (300 ms)
        CompletableFuture<BigDecimal> reading = new CompletableFuture<Void>()
                .completeOnTimeout(null, 300, TimeUnit.MILLISECONDS)
                .thenApply(nothing -> switch (code) {
                    case "EUR" -> BigDecimal.ONE;
                    case "USD" -> new BigDecimal("1.17");
                    case "GBP" -> new BigDecimal("0.87");
                    case "CHF" -> new BigDecimal("0.94");
                    default -> throw new IllegalArgumentException("unknown currency: " + code);
                });
        // im Fehlerfall entfernen wir die Operation aus dem Cache, damit ein späterer Lesezugriff es erneut versucht
        return reading.whenComplete((rate, e) -> {
            if (e != null) {
                cache.remove(code);
            }
        });
    }

    int nbServerAccesses() {
        return nbServerAccesses.get();
    }

    int nbReadings() {
        return nbReadings.get();
    }

    Set<String> cachedCurrencies() {
        return new TreeSet<>(cache.keySet());
    }
}

    9.10.2. Rückkehr zum GUI-Thread

    Das Programm [Async06.java] hat gezeigt, dass eine Fortsetzung je nach Fall entweder von dem Thread, der die Operation abschließt, oder von einem Thread des gewählten Executors ausgeführt wird. In einer grafischen Anwendung (Swing, JavaFX) ist das wichtig: Eine grafische Komponente darf nur vom UI-Thread manipuliert werden. Java hat keinen Mechanismus, der den Rest des Codes automatisch zu diesem Thread zurückführt; das Programm muss dies selbst veranlassen, entweder indem es der Fortsetzung den richtigen Executor übergibt oder indem es die Werkzeuge der Grafikbibliothek verwendet:

    • Mit Swing bewirkt *[SwingUtilities.invokeLater(action)] , dass die Aktion vom Thread der Oberfläche ausgeführt wird; die Methodenreferenz [SwingUtilities::invokeLater] kann als Executor für eine Fortsetzung dienen: [download.thenAcceptAsync(page -> textArea.setText(page), SwingUtilities::invokeLater)]******. Die Klasse [SwingWorker] stellt ebenfalls eine Methode bereit, [doInBackground], die von einem Hintergrund-Thread ausgeführt wird, sowie die Methoden [process] und [done]*, die vom Thread der Oberfläche ausgeführt werden;
    • Mit JavaFX erfüllt [Platform.runLater(action)] denselben Zweck, und die Klassen [Task] und [Service] aus [javafx.concurrent] kapseln einen Hintergrundprozess samt seinem Fortschritt.

    In allen Fällen gilt dieselbe Regel: Der UI-Thread darf niemals warten ([join()], [get()], blockierende E/A), sonst friert das Fenster ein. Die lang laufende Aufgabe wird von einem anderen Thread ausgeführt (zum Beispiel einem virtuellen Thread), und nur die abschließende Aktualisierung der Komponenten übernimmt der Thread der Oberfläche.

    9.10.3. Einen CompletableFuture manuell beenden

    Manchmal muss man eine API verwenden, die ihre Ereignisse über Listener meldet (Kapitel 7), während der übrige Code mit [CompletableFuture] geschrieben ist. // verwandelt die Benachrichtigungen des Thermometers in ein CompletableFuture
CompletableFuture<Double> waitForTemperature(Thermometer thermometer, double threshold) {
    // ein CompletableFuture, das wir selbst abschließen werden
    CompletableFuture<Double> result = new CompletableFuture<>();
    // der Listener schließt das CompletableFuture ab, wenn der Schwellenwert erreicht ist
    DoubleConsumer listener = temperature -> {
        if (temperature >= threshold) {
            result.complete(temperature);
        }
    };
    thermometer.addListener(listener);
    // unabhängig davon, wie es endet (Schwellenwert, Timeout, Abbruch), entfernen wir den Listener
    result.whenComplete((temperature, e) -> thermometer.removeListener(listener));
    // das CompletableFuture wird sofort zurückgegeben; es wird später abgeschlossen
    return result;
}

final AtomicInteger inProgress = new AtomicInteger();

long start;

void main() {
    start = System.nanoTime();
    List<String> pages = IntStream.rangeClosed(1, 9).mapToObj(i -> "page" + i + ".html").toList();
    // höchstens 3 Downloads gleichzeitig: ein Semaphor mit 3 Berechtigungen

                    download(page);

                    permits.release();

                return null;

    9.11.2. Erzeuger / Verbraucher: BlockingQueue

    Das vorige Kapitel hat das Modell Erzeuger/Verbraucher eingeführt: Erzeuger legen Elemente in eine Warteschlange, Verbraucher entnehmen sie. // der Producer: eine Bestellung alle 50 ms
Void produce(int nbOrders) throws InterruptedException {
    for (int i = 1; i <= nbOrders; i++) {
        Thread.sleep(50);
        // offer legt die Bestellung sofort ab, wenn in der Warteschlange Platz ist
        if (queue.offer(i)) {
            display("P  : order " + i + " queued");
        } else {
            // Warteschlange voll: put wartet, bis ein Platz frei wird
            display("P  : queue full, order " + i + " waits");
            queue.put(i);
            display("P  : order " + i + " queued");
        }
    }
    // es wird nichts mehr erzeugt: wir legen die Endmarkierung ab
    queue.put(END);
    display("P  : end of production");
    return null;
}

// ein Consumer: die Bearbeitung einer Bestellung dauert 400 ms
Void consume(String name) throws InterruptedException {
    while (true) {
        // take wartet, bis eine Bestellung in der Warteschlange ist
        int order = queue.take();
        if (order == END) {
            // wir legen die Endmarkierung für den anderen Consumer wieder in die Warteschlange
            queue.put(END);
            break;
        }
        display(name + " : processing of order " + order);
        Thread.sleep(400);
    }
    display(name + " : no more orders");
    return null;
}

    9.13. Strukturierte Nebenläufigkeit (Überblick)

    In den bisherigen Beispielen laufen die von einem Programm gestarteten Operationen unabhängig von diesem: Schlägt eine fehl, laufen die anderen weiter; wird der Code, der sie gestartet hat, unterbrochen, laufen sie ebenfalls weiter; und nichts zwingt diesen Code, auf ihr Ende zu warten. Die strukturierte Nebenläufigkeit schlägt vor, eine Gruppe von Teilaufgaben als einen einzigen Block zu behandeln: Sie werden innerhalb eines Gültigkeitsbereichs (Scope) gestartet, der Scope wartet auf ihren Abschluss, und wenn eine fehlschlägt, werden die anderen abgebrochen. Die Klasse [StructuredTaskScope] setzt diese Idee mithilfe virtueller Threads um. Sie ist seit Java 21 verfügbar, befindet sich aber in Java 25 weiterhin im „Preview“-Status : Ihre API kann sich noch ändern, und ein Programm, das sie verwendet, muss mit der Option [--enable-preview] kompiliert und ausgeführt werden. Sie ist daher nicht Teil der Kursübungen; der folgende Code (Datei [preview/StructuredConcurrency.txt], zum Testen in eine Datei mit dem Namen [StructuredConcurrency.java] zu kopieren) vermittelt einen Eindruck von ihrer Funktionsweise:

    // strukturierte Nebenläufigkeit: Preview-API in Java 25
// Ausführung: java --enable-preview StructuredConcurrency.java
import java.util.concurrent.StructuredTaskScope.Joiner;
import java.util.concurrent.StructuredTaskScope.Subtask;

void main() throws InterruptedException {
    // 1 - zwei Teilaufgaben, die beide erfolgreich sein müssen
    try (var scope = StructuredTaskScope.open()) {
        Subtask<Integer> angers = scope.fork(() -> readTemperature("Angers", 1000));
        Subtask<Integer> brest = scope.fork(() -> readTemperature("Brest", 500));
        // join wartet auf das Ende der Teilaufgaben; schlägt eine fehl, wird die andere abgebrochen
        // und join wirft eine Exception
        scope.join();
        IO.println("Angers: " + angers.get() + ", Brest: " + brest.get());
    }
    // 2 - die erste Antwort genügt: die anderen Teilaufgaben werden abgebrochen
    try (var scope = StructuredTaskScope.open(Joiner.<Integer>anySuccessfulResultOrThrow())) {
        scope.fork(() -> readTemperature("mirror-paris", 800));
        scope.fork(() -> readTemperature("mirror-lyon", 300));
        IO.println("first answer: " + scope.join());
    }
}

int readTemperature(String city, long duration) throws InterruptedException {
    Thread.sleep(duration);
    return 10 + city.length();
}

    // Anwendung: die Steuerberechnung, mit von virtuellen Threads ausgeführter Ein-/Ausgabe
// - die Stufen werden aus [TaxData.txt] gelesen, die Steuerpflichtigen aus [taxpayers.txt]
// - die Ergebnisse werden in [results.txt] geschrieben
// eine korrekte Zeile eines Steuerpflichtigen: verheiratet (y/n), Anzahl der Kinder, Jahresgehalt
static final Pattern TAXPAYER = Pattern.compile("([yn])\\s+(\\d+)\\s+(\\d+)");

void main() {
    Path results = Path.of("results.txt");
    try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
        // die beiden Eingabedateien werden gleichzeitig von zwei virtuellen Threads gelesen
        Future<List<TaxBracket>> bracketsReading = executor.submit(
                () -> loadBrackets(Path.of("TaxData.txt")));
        Future<List<String>> taxpayersReading = executor.submit(
                () -> Files.readAllLines(Path.of("taxpayers.txt")));
        // die Berechnung wartet auf die beiden Lesevorgänge und schreibt dann die Ergebnisse
        Future<Integer> processing = executor.submit(
                () -> calculateTaxes(bracketsReading.get(), taxpayersReading.get(), results));
        try {
            // die gesamte Verarbeitung ist auf 10 Sekunden begrenzt
            int nbResults = processing.get(10, TimeUnit.SECONDS);
            IO.println(nbResults + " lines written in [" + results + "] :");
            IO.print(Files.readString(results));
        } catch (TimeoutException e) {
            processing.cancel(true);
            IO.println("processing abandoned: timeout exceeded");
        }
    } catch (ExecutionException e) {
        // der Fehler eines Lesevorgangs wird doppelt eingepackt: vom Lesen und von der Berechnung, die darauf gewartet hat
        Throwable cause = e.getCause();
        while (cause instanceof ExecutionException) {
            cause = cause.getCause();
        }
        IO.println("error: " + cause.getClass().getSimpleName() + " : " + cause.getMessage());
    } catch (IOException | InterruptedException e) {
        IO.println("error: " + e.getClass().getSimpleName() + " : " + e.getMessage());
    }
}

// liest die Steuerstufen (limit:coeffR:coeffN, Dezimalpunkt)
List<TaxBracket> loadBrackets(Path file) throws IOException {
    try (Stream<String> lines = Files.lines(file)) {
        return lines.filter(line -> !line.isBlank()).map(TaxBracket::parse).toList();
    }
}

// berechnet die Steuer jedes Steuerpflichtigen und schreibt die Ergebnisse
int calculateTaxes(List<TaxBracket> brackets, List<String> taxpayers, Path output) throws IOException {
    try (BufferedWriter writer = Files.newBufferedWriter(output)) {
        for (String line : taxpayers) {
            Matcher fields = TAXPAYER.matcher(line.trim());
            String result = fields.matches()
                    ? "tax = " + calculateTax(brackets, fields.group(1).equals("y"),
                            Integer.parseInt(fields.group(2)), Integer.parseInt(fields.group(3))) + " €"
                    : "incorrect line";
            writer.write(String.format("%-12s : %s", line, result));
            writer.newLine();
        }
    }
    return taxpayers.size();
}

// die Steuerberechnung (Steuertarif 2004 auf Einkommen 2003, für die Übung beibehalten)
int calculateTax(List<TaxBracket> brackets, boolean married, int nbChildren, int salary) {
    BigDecimal shares = BigDecimal.valueOf(nbChildren).divide(BigDecimal.TWO)
            .add(BigDecimal.valueOf(married ? 2 : 1));
    if (nbChildren >= 3) {
        shares = shares.add(new BigDecimal("0.5"));
    }
    BigDecimal income = new BigDecimal("0.72").multiply(BigDecimal.valueOf(salary));
    BigDecimal quotient = income.divide(shares, MathContext.DECIMAL64);
    // die erste Stufe, deren Grenze den Familienquotienten übersteigt, andernfalls die letzte
    TaxBracket bracket = brackets.stream()
            .filter(t -> quotient.compareTo(t.limit()) <= 0)
            .findFirst()
            .orElse(brackets.getLast());
    return bracket.coeffR().multiply(income).subtract(bracket.coeffN().multiply(shares)).intValue();
}

// eine Steuerstufe
record TaxBracket(BigDecimal limit, BigDecimal coeffR, BigDecimal coeffN) {
    static TaxBracket parse(String line) {
        String[] fields = line.split(":");
        return new TaxBracket(new BigDecimal(fields[0]), new BigDecimal(fields[1]),
                new BigDecimal(fields[2]));
    }
}

    9.15. Die goldenen Regeln

    Fassen wir die Regeln der asynchronen Programmierung in Java zusammen:

    • Zum Warten keinen System-Thread blockieren: Ein Wartevorgang (Ein-/Ausgabe, Timeout oder eine andere Operation) erfolgt entweder in einem virtuellen Thread oder indem eine Fortsetzung an ein [CompletableFuture] angehängt wird;
    • Für neuen Code virtuelle Threads bevorzugen: blockierenden, sequenziellen und lesbaren Code schreiben (Schleifen, [try / catch], gewöhnliche lokale Variablen), ausgeführt von [Executors.newVirtualThreadPerTaskExecutor()]; ein virtueller Thread pro Aufgabe, niemals einen Pool virtueller Threads verwenden;
    • [CompletableFuture] verwenden, um Operationen zu verknüpfen oder eine API zu nutzen, die [CompletableFuture] zurückliefert ([HttpClient.sendAsync], reaktive Bibliotheken); dann wählt man den Executor der Fortsetzung ([xxxAsync(..., executor)]) und führt niemals eine blockierende Operation im gemeinsamen Pool aus;
    • Kein [join()] oder [get()] in einer Fortsetzung oder in einem GUI-Thread: Diese Wartevorgänge blockieren den Thread, der sie ausführt. Sie gehören ins Hauptprogramm oder in einen virtuellen Thread;
    • Virtuelle Threads dienen dem Warten, nicht dem Rechnen: Für Berechnungen verwenden Sie einen Pool von Plattform-Threads, dessen Größe sich nach der Anzahl der Prozessoren richtet, oder parallele Streams;
    • Den Zugriff auf knappe Ressourcen mit einem [Semaphore] begrenzen, nicht über die Größe eines Thread-Pools;
    • Abbruch ist kooperativ: Eine Aufgabe wird über [Future.cancel(true)] abgebrochen, was ihren Thread unterbricht; eine unterbrochene Aufgabe beendet sich ordnungsgemäß; eine [InterruptedException] wird niemals verschluckt (sie wird entweder weitergereicht, oder das Interrupt-Flag wird wieder gesetzt). Und denken Sie daran, dass [CompletableFuture.cancel] nichts unterbricht;
    • Wartezeiten begrenzen: [orTimeout], [completeOnTimeout], [get(timeout, unit)]; und die Operation selbst beenden, wenn das Warten aufgegeben wird;
    • Erst starten, dann warten: Um mehrere unabhängige Operationen gleichzeitig auszuführen, starten Sie alle und warten dann auf sie ([allOf], [invokeAll], die Methode [close] des Executors);
    • Auf eine gestartete Operation muss gewartet werden, oder sie muss überwacht werden: Eine vergessene Operation verbirgt ihre Ausnahmen ([exceptionally], [whenComplete] dienen zu ihrer Behandlung); indem man eine [CompletionException] oder eine [ExecutionException] zurückverfolgt, sucht man die eigentliche Ursache.
